Known bugs
----------
FIXED (July 2026), pending play-test on the pics build: Zork Zero's drop-cap
paragraphs. The illuminated initial was overwritten by the paragraph's first
line, the first line wrapped a word too late (the "d" of Flathead landed on
the screen's rightmost column), and the text never came back to the left
edge under the picture. Three causes, all in the same dance the game does
around routine 1c9a2 (txd):
1. set_margins did not restart the print buffer, so the paragraph printed
   from the column captured before the margin moved - the first line began
   at the picture's left edge (and the buffered-wrap bookkeeping, fed a
   start column left of .buffer_left, produced the stray "d"). set_margins
   now flushes and restarts buffering around the cursor move, like
   set_cursor does.
2. Window property 8/9 - the newline interrupt - was not implemented: the
   game counts the picture's rows in the countdown (property 9) and resets
   the margins from the routine (property 8) when they are past. Property 8
   is a packed address, a word, so it gets a high-byte array beside
   window_linecount_hi (the byte slot used to truncate it silently).
   increase_num_rows now decrements the countdown on each completed line
   and calls the routine like a timed-input interrupt (stack_call_routine
   mode $80 + z_execute), saving everything the in-flight print relies on
   (z_address and the zchar state, the operand array, z_temp, the buffer
   indices - neutralized so a nested set_margins flush cannot reprint the
   line being wrapped). Shogun uses the same mechanism for its border
   pictures. The wrap path fires the interrupt before the carried-over
   word is placed and recomputes the margins for it (spec order); testz6
   has the case and matches dfrotz on the C64.
3. z-spec 8.8.3.2.2.1: interpreter 6 running exactly Zork Zero r393.890714
   must fire the interrupt only after the cursor has moved to the new line
   - the game sets its countdown one lower on that interpreter. make.rb
   defines ZORK0_MSDOS_QUIRK for that story + TERPNO combination (our pics
   builds), and the firing point defers accordingly. The text builds claim
   interpreter 8, where the game uses the standard order - both orders
   stay exercised.
   Verified: testz6's newline-interrupt and margin cases match dfrotz on
   the C64; Shogun's X16 menu page still matches the reference; Arthur,
   Journey unaffected (neither uses the interrupt). The MEGA65 zorkzero-pics-mega65
   build compiles and awaits the windowed play-test (headless stops at the
   picture-disk swap prompt; the drop-cap pillars are on disk 2).

FIXED (July 2026), the follow-up pair to the parser-message fix below, found
by comparing against sfrotz (z6games/z6specialmessage.png):
1. Printing the message used to raise a [More] prompt. Arthur's message
   window is one line tall and non-scrolling, and sfrotz never pauses there:
   a [More] only makes sense where text scrolls away unread. increase_num_rows
   now requires WIN_SCROLLING (window 0 has it, windows 1-7 default off). At
   the same time the line count became the signed word the spec requires
   (window_linecount_hi): games park it at -999 to postpone [More] and 999
   means never (8.8.3.2.6) - Arthur puts -999 into window 0 after its intro
   keypresses, which the old byte array truncated to 25, a value that made
   window 0 [More] on the *next* newline. put/get_wind_prop and erase/clear
   handle both bytes.
2. The message wasn't "bold". Arthur prints it by reading the current
   window's colour pair (get_wind_prop -3 property 11, bg high byte / fg low,
   8.8.3.2.4), calling set_colour with the pair swapped, erasing the window
   and print_forming into it - i.e. reverse video, like its status line.
   Ozmoo's property 11 was a never-written byte, so the swap became
   set_colour 0,0 = "no change". set_colour now keeps each window's pair
   (window_colour, nybble-packed; operands 0/-1 keep, 1 is the default) and
   get_wind_prop answers it; when a set_colour is an exact swap of the
   current pair (new fg = screen bg, new bg = old fg), s_colour_swap renders
   everything as reversed glyphs with the field in the old foreground - no
   target has per-window hardware backgrounds, but a swapped pair is exactly
   what the reversed glyph draws. The real colours stay put; the un-swap
   switches it off. ECM (no reversed glyphs) keeps the tracking only.
   En route this turned up that erase_window took its operand raw, so
   Arthur's erase_window -3 indexed the window arrays 253 bytes out (writing
   window_y_cursor+253!) and never actually erased - the band was invisible
   and memory was scribbled on every parser error. It goes through
   window_from_operand now, like every other window-numbered opcode.
   Verified on C64 (band reversed full width, [More] gone over ~750 empty
   commands, intro/status unchanged) and arthur-mega65; testz6 C64/-fcm:40/
   -fcm screens byte-identical to before. The sfrotz "grey" is just its
   default scheme - the band now reverses whatever scheme Ozmoo runs
   (-fgcol:/-bgcol: pick another; darkmode still works).

FIXED (July 2026): an empty command or an unknown word at Arthur's prompt
printed "I beg your pardon?" and then gibberish forever, on every target (the
mega65 screenshot was z6games/z6error.png). Not a PC desync and not corrupt
attic RAM: Arthur buffers its parser complaints with the v6 three-operand form
"output_stream 3 table width" (routine 111ac in txd's disassembly, width 0 =
wrap to window 0), counts the buffered lines, and re-prints them with
print_form into a pop-up window 3. With a width operand the table must be in
the print_form format - one record per wrapped line, a length word then the
characters, ended by a zero word - but streams.asm ignored the third operand
and always wrote the plain v5 format (count word + raw text). print_form then
read the count word (18) as "line 1 is 18 characters", which is why the
message itself printed correctly, and walked garbage from there until a zero
word happened to stop it; the garbage line count also fed scroll_window and
window_size. Normal commands never touch this path, which is why only parser
errors broke. streams.asm now word-wraps into the record format when the
width operand is present (>= 0 names a window whose width is used, < 0 is a
box -width units wide - the z-spec 1.0/dfrotz convention; all Infocom v6
games pass 0). All four v6 games use the three-operand form, always with
width 0; only Arthur print_forms the result. Verified against dfrotz with new
testz6 cases (record lengths, wrap points, embedded newline) on C64, -fcm:40
and -fcm, and the repro itself on C64 and arthur-mega65: thousands of empty
commands now leave a clean "I beg your pardon?" line.

FIXED, and confirmed in play (July 2026): under -fcm, Arthur used to drop or
change the odd character in the body text, differently on each run - one run
gave "Anne's Day, Compline hurchyard" and "sudtenly", the next "-AY" and
"suddtnly". Zork Zero's banquet paragraph lost text the same way. That it varied
between runs pointed at something timed, and it was: CBDOS rewrites colour bytes
around $7f2-$7fb on every disk access, which in FCM's 16 bit colour cells land
in attribute bytes, where $f8 is a GOTOX token that blanks the rest of the row
(the same root cause as the white stripe over Arthur's intro pictures - see the
FIXED entry below). Moving the screen's colour region to FCM_COLOUR_OFFSET
($0800) put it out of the way. Play-tested since: Arthur's prologue, its first
room description and its status line are all clean. Zork Zero's banquet
paragraph has not been re-checked specifically, but it was the same bug.

FIXED: after the 16-bit picture index work, Arthur's churchyard scene stopped
appearing (the frame drew, its middle stayed blank background). picture_data's
rect path (.pd_try_rect) called .rect_find with the picture number expected in
x, but the new 16-bit .pic_find clobbers x (it uses it as a table-address high
byte for .pic_addr, where the old one-byte version kept the number in x the
whole loop). So picture_data on a Rect placeholder searched for a garbage
number and returned the wrong size; Arthur laid the scene out from that and
drew it at y=253, off the bottom of the screen, where pic_fill_cells clips
every row. The fix is one line: reload x from z_operand_value_low_arr before
.rect_find, as draw_picture's own .dp_not_image path already did. Found with a
ring buffer logging every draw_picture's index and computed y - it showed pic 4
at y=252 while everything else was on screen.

DONE: per-pixel compositing. A small picture drawn over a scene - Arthur's
stone over the churchyard - used to sit in a white rectangle, because under
-fcm a pixel value of 0 is transparent and shows the screen background, not the
picture behind. Only fully transparent cells ($ffff) were revealing what was
underneath. pic_fill_cells now, before writing an opaque cell, reads what is
there, and if a full colour tile is under it bakes a fresh tile (.pcf_make_tile)
taking the overlay's pixel where opaque and the underlying tile's pixel where
transparent - which the store's absolute palette indices (all banks loaded at
once) make legal. Matches the reference. The composite tiles come off
pic_next_tile; a game that redraws full-screen pictures over each other without
clearing churns the store, and that predicted corruption arrived as Arthur's
intro stripe (below), so .pcf_make_tile now skips compositing for fully-opaque
cells.

FIXED: the white stripe across Arthur's full-screen intro pictures - and,
almost certainly, the "games drop or change the odd stretch of body text"
bug, which had the same root cause. Not a write into the tile store's banks
at all: the first 2 KB of colour RAM is also mapped at $1f800-$1fffff in bank
1, whose top is CBDOS workspace, so every SD/disk access rewrites colour
bytes around $7f2-$7fb. The 40-column screen's 2000 colour bytes stop just
short of them; the 80-column screen's 4000 reach row 12 cell 57, and the
DOS's $f8 bytes have bit 4 set - a VIC-IV GOTOX token in FCM's 16-bit colour
cells, which blanks the rest of the row from that cell on. Hence a white
stripe over the last fifth of a middle picture row, and text lines losing
their tails "differently on each run" (whenever disk access had scribbled
since the row was last printed). Diagnosed in xemu by dumping the stripe
cells (valid tile codes, garbage colour flag bytes) and then watching
$ff807f0 through the boot: the bytes tick during every disk phase. The fix
moves the screen's colour region off the DOS bytes with the VIC-IV colour
offset ($d064/5): FCM_COLOUR_OFFSET = $0800 (constants.asm), added to
zp_colourline everywhere it is computed; scrollback's temporary colour moved
to $1000 to stay clear of it; quit puts the offset back to 0 for BASIC.
Verified: Arthur's sword-and-chapel and Merlin intro pictures render
pixel-clean, and testz6 still matches dfrotz at both 40 and 80 columns.

FIXED, found on the way: drawing a full-screen picture over another (or
redrawing one over itself, which Arthur's intro does) baked a composite tile
for every cell - ~1850 allocations on a 2048-tile store - wrapping
pic_next_tile into the picture's own run and overwriting source tiles that
later, deduplicated cells still needed. This was the todo entry above coming
true, as garbled borders and bottom band on the intro pictures rather than as
the stripe. .pcf_make_tile now counts the overlay tile's transparent pixels
while copying it into the work buffer; a fully opaque cell keeps its own
screen code and allocates nothing.

FIXED: the store (2048 tiles) cannot hold two big pictures at once - Arthur
draws the Merlin scene (1057 tiles) centred over the sword picture (1223),
whose gold frame stays visible - so recycling the sword's tiles showed
garbage around the smaller picture. .pic_alloc now compacts instead of
wrapping (.pic_gc): when a fresh run will not fit, every tile still shown by
a cell outside the incoming picture's rectangle is kept, moved to the bottom
of the store in ascending order (a survivor can only move down, so the copy
is safe in place), and its cells repointed; the new run lands above the
survivors. ~500 frame tiles + 1057 fit easily. The rewrite works from a
bitmap, per-byte prefix counts and a popcount table (~1.3 KB of tables); the
whole sweep is a few hundred thousand cycles at 40 MHz, and it only runs
when the allocator would otherwise wrap. If even the survivors plus the new
picture do not fit, the old wrap-to-zero remains as the fallback. Verified:
Merlin renders inside the sword picture's intact frame, matching the
reference, and the churchyard screen still composites correctly after the
GC has run.

FIXED: Arthur's "FATAL ERROR: 17" on the MEGA65 was a missing window property.

get_wind_prop's property 13 is the font size: height in the high byte of the
word, width in the low one. window_font_size was declared in screen-z6.asm and
never written, so it read back as 0. txd shows what Arthur does with it:

    11168:  GET_WIND_PROP   #00,#0d -> -(SP)      ; window 0, font size
    1116e:  LOG_SHIFT       (SP)+,#fff8 -> -(SP)  ; >> 8, the height
    11175:  AND             (SP)+,#ff -> G87
    11179:  GET_WIND_PROP   #00,#0d -> -(SP)
    1117f:  AND             (SP)+,#ff -> G18      ; the width

and then, at $9d54, "MOD L00,G87" - a modulo by zero.

The fix: get_wind_prop answers 1,1 for property 13, because the header tells the
game a character is one unit each way, and window_font is initialised to 1, the
normal font. Property 13 is the only window property that is a real word, so it
cannot live in the byte-per-window arrays with the others.

This was never a MEGA65 bug. The C64 executed the same modulo by zero and did
not notice, because make.rb compiles CHECK_ERRORS into MEGA65 builds only
(`if $target == "mega65"`). Both targets were also computing Arthur's whole
layout from a zero font width; with the fix, the status line and the body text
land where they should, on both.

How it was found: DEBUG + TRACE make fatalerror print the last ten opcodes with
their z_pc, which named the instruction; ztools' txd then named the property.
Both are worth reaching for early - see CLAUDE.md.

Two dead ends worth not repeating, both disproved along the way:
- It is not a large memory problem. A generated v6 story of 276 KB (1700 filler
  routines, `inform -v6 -B`) calls a routine, passes arguments to it, prints a
  string and reads globals all from above $40000, and the MEGA65 gets every
  answer right. Z-machine byte addresses are 16 bit, so loadb/loadw cannot reach
  above 64 KB anyway; only code and strings live up there, and those work.
- It is not the timed-input interrupt, which had never been tested for z6 on any
  target. A v6 test doing `@read_char 1 10 Ticker` and `@aread buf par 10 Ticker`
  gives "read_char -> 0 ticks 3" and "aread -> 0 ticks 3" on the C64 and the
  MEGA65 alike, which is correct.
- 2OP:23 is div and 2OP:24 is mod, and z_divide serves both. Tracing z_ins_div,
  finding no hits, and concluding the MEGA65's PC had diverged cost an
  afternoon. It had not: z_ins_mod fires on the C64 at the same z_pc, $009d57.

Note in passing: fatalerror's non-DEBUG path does `stx SCREEN_ADDRESS + 79`, a
cell offset used as a byte offset. Under -fcm that writes the high byte of cell
39 instead of the character of cell 79. Harmless - it is the error code, on a
screen that is about to reset - but it is the same class of bug as the three the
FCM work turned up.

Still to do for z6 (not crashes):
- These machines will never draw pictures. draw_picture writes a "pic:N" note
  where the picture belongs instead, straight to the screen so that it stays
  out of the transcript, and without moving the game's cursor. erase_picture
  paints over a note of the same width. Both trust the game's y,x (or the
  cursor when either is zero), so a note lands where a picture would have,
  but nothing knows how large the real picture was.
- picture_data never branches, since no picture number is ever valid, and
  reports zero pictures and release 0 for picture 0. picture_table is a
  caching hint with nothing to cache, and make_menu branches false: both are
  correct as they stand, not stubs.
- read_mouse and mouse_window work, and the click is confirmed: the MEGA65 full
  colour screen has a mouse (asm/mouse.asm), sprite 0 is a red pointer, a click
  is input code 254 with its position (in cells) in the header extension table,
  and read_mouse reports the live pointer. The mouse is on control port 2: the
  pots ($d620/$d621) and the button ($dc00 bit 4) are both there. Port 1's fire
  bit is shared with keyboard row 4, so it can't tell a click from SPACE - that
  was the bug that made clicks do nothing. Verified on xemu: Zork Zero's compass
  rose responds. A real MEGA65 mouse in port 1 would need the port-1 registers.
  The X16's pictures screen has a mouse too (July 2026), gated on the same
  Z6_MOUSE: there the KERNAL owns it, so mouse_config ($ff68) shows the pointer
  and bounds it (80x25 cells, in 8-pixel units), mouse_get ($ff6b) reads the
  position and buttons, and the KERNAL's interrupt handler scans the mouse and
  moves VERA sprite 0 (image at VRAM $13000, clear of the tile store and the
  layer 0 map) - so only .mouse_read differs between the two machines. Verified
  headlessly: x16emu under Xvfb, xdotool to move and press, ctrl+s to dump RAM.
  That port also refactored mouse.asm into a shared part (the press edge, the
  click cell, the header extension table, the mouse window) and a per-machine
  .mouse_read; the MEGA65 click was re-checked by hand afterwards and still
  works. Text-only z6 has no pointer on either machine.
- scroll_window scrolls whole character cells, because the header tells the
  game a character is one unit wide and one high. It ignores the scroll delay
  and smooth scrolling that .s_scroll has to honour.
- set_margins is now used for word wrapping, and erasing a window puts the
  cursor on the left margin. The margins do not clip set_cursor, erase_line,
  erase_window or scroll_window, which all still work on the whole window,
  as the spec intends.
- print_form is fully implemented: it is a text opcode, not a graphics one.

Z6 on other targets
-------------------
The window model now works on every target Ozmoo supports: the C64 first, then
the Plus/4, the MEGA65, the X16, and finally the C128's 80 column (VDC) screen.
- ECM (-ecm) is C64 only, and make.rb rejects it elsewhere. The MEGA65 and X16
  don't need it: their video chips give every character its own background
  colour, so those targets should set the window's background directly rather
  than borrowing the ECM approach.

DONE: the z6 window model on the C128's 80 column screen. This was the last
target still scrolling the whole screen, and the fix is the same shape as the
X16's: .s_scroll_vdc now goes through the shared .calc_window_rect /
.sw_up_one / .sw_blank_row helpers, and only the row copy (.vdc_copy_row) is
VDC-specific. s_scroll_window's "80 columns are not handled" early return is
gone, so the scroll_window opcode works there too.
- The VDC's screen is not in the CPU's address space, but the chip has a
  blitter: with the copy bit of the vertical scroll register (24) set, writing
  a byte count to VDC_COUNT (30) copies that many bytes from the copy source
  address (32/33) to the current address (18/19). So a window row is one
  register write instead of 80 read/write round trips through the data port.
  Characters live at $0000 and their attributes at $0800, so a row is copied
  twice, once per region (the attributes only under COLOURFUL_LOWER_WIN, which
  z6 always sets, since Z6 implies Z5PLUS).
- A count of 0 means 256 bytes, not none, so .vdc_copy_row returns early for a
  window with no columns rather than blitting a quarter of the screen.
- .sw_blank_row needed nothing: it blanks through s_delete_cursor, which
  already dispatches to VDCPrintChar in 80 column mode. Note that it does so
  before loading y from zp_screencolumn, so y must hold the column on entry -
  which every caller already arranges.
- The old .s_scroll_vdc also refused to scroll until the cursor had passed the
  bottom of the *screen* (its "cmp s_screen_height / bpl" guard), which is the
  same bug the X16's had: a window that did not reach the bottom never
  scrolled at all. The caller has already checked the window's own edge.
Verified under VICE (x128) by dumping VDC RAM through the monitor - the screen
is not in the CPU's address space, so the dump needs "bank vdc; m 0000 07cf" as
one command, and note that VICE's -80col does not reach the kernal's 40/80 flag
under -default, so the test pokes $d7 = $80 at program_start instead (a
tracepoint on program_start with "> d7 80"). testz6scroll then renders on the
VDC exactly as it does on the C64: the window scrolls to "line 6".."line 10"

DONE: pictures on the X16 (-pics without -fcm; make z6-pics-x16 /
arthur-pics-x16, and the other three games have targets too). The design is
the MEGA65 FCM engine ported to VERA (asm/pictures-x16.asm; the shared
opcode plumbing in screen-z6.asm now splits per target around the engine):
- The screen is two layers: text stays on layer 1, and the pictures live
  behind it on layer 0, a 64x32 map of 16x8-pixel 4bpp tiles. VSCALE is
  halved and VSTOP crops to 640x200 effective - the MEGA65 80-column
  geometry, so `dfrotz -h 25 -w 80` and the MEGA65 build stay the
  references. SCREEN_HEIGHT is 25 under Z6_PICTURES (constants-x16.asm)
  and the build reports interpreter 6 (IBM), like the MEGA65 pics builds.
- One tile is one logical art cell (8x8 art pixels doubled horizontally at
  bake time). The store is all of VRAM bank 0 - 1024 tiles, tile 0 reserved
  as the transparent tile - and the map, the relocated charset and the text
  screen share bank 1. A map entry carries the tile index and a palette
  offset nybble, which is how each picture keeps its own 16-colour bank
  (banks 1..14 above the text colours): the bank rides in the map cells,
  not the pixels, so nothing is rebaked when a bank is reassigned.
- No preload: a picture is LOADed from SD on demand, uncompressed, into a
  4-bank staging area just above the story (PIC_STAGING_BANK from make.rb),
  and the staged picture is cached so redrawing the frame or the status
  icons never touches the card. No picture disks, no swap prompts - Zork
  Zero's 396 files just sit in the game directory. picture_data answers
  from assembled-in pic_width/pic_height tables (the picture asked about
  is usually not the one staged), which pics2asm's --x16 mode emits.
- The allocator, the GC (compact instead of wrap) and per-pixel
  compositing are the MEGA65's, reworked for VERA's data ports: the GC
  walks the layer 0 map instead of screen RAM, and a composite cell has
  ONE palette bank, so pixels kept from the underlying picture are
  translated into the overlay's bank (exact colour match, else nearest by
  RGB distance over CPU-side palette copies).
- The text layer cannot bury a picture the way a one-plane screen does, so
  drawing a picture blanks the text cells it covers (space, background
  nybble 0 = transparent) - the MEGA65's replace-the-text semantics -
  and erase_picture / erase_window restore opaque background and clear the
  layer 0 cells. The undo buffer moved from VRAM (which the tile store now
  owns) to banked RAM above the staging area; quit restores the composer
  and switches layer 0 off so BASIC comes back readable.

The plan for z6 on the MEGA65
-----------------------------
The C64 and the Plus/4 will never draw pictures, and keep the "pic:N" notes
whatever happens below.

Screen size, and why 320x200
  Arthur was an Amiga game at 320x200, and z6games/arthur-graphics is scaled to
  that: all 137 pictures fit, the largest being 292x196. So the MEGA65 z6 screen
  is 320x200 in FCM with 16 bit character codes: 8x8 cells, 40x25 of them.

  That is not only the natural fit for the art, it is the only size that fits in
  memory. An FCM cell needs 64 bytes of character data, so a worst case full
  screen picture is 1000 x 64 = 62.5 KB of tiles. At 640x400 it would be 80x50 =
  4000 cells = 250 KB, and there is nowhere to put that. Screen RAM (2000 bytes)
  and colour RAM (2000 bytes) at 40x25 with two bytes per cell are exactly the
  sizes the current 80x25 8 bit mode already uses, so neither grows.

  Fast RAM is 384 KB, and the techreport's map spends most of it: $00000-$0ffff
  interpreter, $20000-$3ffff ROM, $40000-$4ffff sound effect, $50000-$5ffff undo.
  That leaves bank 1, $10000-$1ffff, 64 KB, unclaimed. 62.5 KB of tiles fit there
  with 1.5 KB to spare, so sound and undo both survive and nothing has to be
  sacrificed. It is knife-edge, and it assumes two things that step 2 has to
  confirm: that C64 mode really leaves bank 1 alone, and that the text charset
  can live outside those 64 KB, as ordinary 8 byte glyphs for chars 0-255 with
  full colour only for chars 256 and up (what the VIC-IV's FCLRLO/FCLRHI split is
  for). There is no room for double buffering. If it does not fit, free
  $40000-$4ffff by dropping sound before giving up any of the above: z6 games do
  not use extended sound.

  8 bits per pixel, not the 4 of NCM, even though no picture uses more than 14
  colours and NCM would halve every figure here. An NCM cell is 16 pixels wide
  and a pixel is a nybble, so a picture at an odd x needs a nybble shift, which
  the DMA engine cannot do and which lands us back in CPU side bitmap shifting.
  At 8bpp a pixel is a byte, any x offset is a byte offset, and m65_run_dma blits
  it directly. Revisit only if memory forces it, or if step 2 shows Arthur's
  draw_picture coordinates are always cell aligned.

  Dropping to 40 columns is right for v6 and wrong for everything else, so this
  is a Z6-conditional fork of the MEGA65 constants, not the new MEGA65 default.
  constants.asm sets SCREEN_WIDTH = 80 for the target unconditionally today.

1. DONE for the MEGA65, against the C64. The earlier headless run stopped at
   the first MORE prompt; driving the prompts from xemu's uartmon (the recipe
   is in CLAUDE.md) gets testz6 all the way to the read prompt. Running the
   same story on both targets and dumping screen and colour RAM:
   - Every line matches, character for character, once each window is scaled to
     its screen width. window_size, move_window, set_margins and the wrapping
     all agree; so do print_form, picture_data, and the pic:N notes, which land
     on their window's top left cell (col 12 on the C64, col 25 on the MEGA65,
     each being the window's x).
   - The MORE prompt appears at the current window's bottom right cell on both.
   - Colour RAM is a clean 8 x 13 rectangle of colour 3 on the C64 and 8 x 26
     on the MEGA65, matching @set_colour 8 7 1 and nothing smeared. That
     exercises the colour2k/colour1k banking in s_scroll_window.
   - testz6 scrolls -1 then +1, which a scroll_window that did nothing would
     also pass. Rebuilt with a single +1 scroll, both targets shift the window
     up one row and both then let erase_picture blank the first five characters
     of "pics 0 rel 0", which the scroll moved under the note. So it really
     scrolls, identically.
   The one apparent difference is a red herring: the MEGA65 dump shows $e0
   where the C64 shows "p", at the start of the pic:12 note. $e0 is CURSORCHAR
   (ozmoo.asm), and draw_picture is supposed to leave the cursor where it found
   it, which is exactly there. The C64 dump was simply taken before the cursor
   was drawn.

   DONE for the Plus/4 too, the same way, under xplus4 (screen $0c00, colour
   $0800). Both builds are character for character identical to the C64, in the
   double scroll and the single scroll variants alike. Its colour RAM holds $63
   inside window 1, which is TED colour 3 at luminance 6 - the right mapping of
   the C64's cyan through plus4_vic_colours, not a low nybble that happens to
   read 3.

   So the three targets that share .s_scroll agree. Nothing here needs fixing
   before the FCM work starts.

2. DONE. tools/png2fcm.py and tools/fcm-prototype.asm; the prototype draws
   Arthur's title screen, and then a smaller picture with a line of text under
   it, on a 320x200 FCM screen with 16 bit character codes. What it settled:

   - Bank 1 is free and the VIC-IV can fetch from it. Tiles DMA'd from the
     program's own RAM to $10000 render.
     Confirmed inside Ozmoo since: stamping 64 signatures across $10000-$1ffff
     at testz6's read prompt and then letting the game finish the read, print,
     scroll its window and quit leaves every one of them intact. Statically,
     every far write in the MEGA65 build goes somewhere else - dynmem and the
     story to attic (dynmem_pointer + 3 = $08, ozmoo.asm), the current sound
     effect to bank 4 (sound.asm), undo to bank 5 (disk.asm, lda #$05),
     scrollback to attic and colour RAM. Nothing addresses bank 1. Not
     exercised at runtime: save, restore, undo, sound, scrollback.
   - The register setup that works, all with hot registers off ($d05d bit 7):
     $d031 = H640 off, V400 off, and ATTR (bit 5) OFF, which is what gives
     8 bit colour - the opposite of what some of the documentation says.
     $d054 = CHR16 (bit 0) on, FCLRHI (bit 2) on, FCLRLO (bit 1) OFF.
     $d05e = 40 chars per row, $d058/9 = 80 bytes per row (two per cell),
     $d060-3 = screen, $d064/5 = colour RAM offset, $d068-a = charset.
   - In FCM the 16 bit screen code is not a character number: it is the pixel
     data address divided by 64. Tiles at $10000 are screen code $0400.
   - FCLRLO off does what we hoped: codes < 256 are ordinary 8 byte glyphs
     from CHARPTR, codes >= 256 are 64 byte full colour tiles. Text and
     picture coexist on one screen. So the text charset costs 2 KB and lives
     outside the tile store, as the budget in step 3 assumes.
   - The palette registers want the nybbles swapped. This is easy to get wrong
     and hard to see: every colour in 1.png is of the form $NN, for which
     swapping is a no-op. Checked against 40.png, whose palette has values like
     $F0; unswapped, its (0,0,240) blue renders as (0,0,8). Swapped, the whole
     picture is exact.
   - Colour RAM is two bytes per cell. Byte 0 is flags (zero), byte 1 is the
     colour for pixel value 255, which no picture pixel is. A single DMA fill
     of zeroes over both is enough.
   - Pixel 0 is transparent and shows the background, so padding a picture out
     to a cell boundary costs nothing visually.
   - Deduplicating cells is worth having and nearly free. Across the 137
     pictures it saves 13% (1155 KB -> 1002 KB). The worst single picture,
     84.png, is 925 cells: 57.8 KB raw, 46.9 KB deduped. Either fits bank 1's
     64 KB, so the step 3 budget holds with room to spare. png2fcm.py always
     dedupes and emits a cell map, which is what screen RAM wants anyway.
   - Not tested: whether DMA can do the scrolling. Nothing suggests it cannot -
     scrolling is a linear copy within screen and colour RAM, and DMA already
     writes colour RAM here - but it has not been run.

   One trap for anyone reading the prototype: it fills screen RAM for all 25
   rows from the cell map, so a picture shorter than the screen ran off the end
   of the map until a row check was added. Arthur's title screen is exactly 25
   cells tall and hid the bug.

3. Rewrite the MEGA65 z6 screen mode to use FCM (full colour mode, VIC-IV,
   with 16 bit character codes) at 320x200, 40x25 cells, as argued above. It
   is needed either way: it gives every character its own background colour,
   which retires the ECM approach on this target, and 16 bit character codes
   are the only sane way to get enough unique tiles for pictures.

   The size of the change is now known. screenkernal-z6.asm has 66 uses of
   zp_screenline / zp_colourline, and nearly all of them are "y holds the
   column, sta (zp_screenline),y writes the cell". Under CHR16 a cell is two
   bytes, so every one of those is affected. Two seams make it tractable:
   - update_screenpos already computes the row address on the MEGA65 with the
     hardware multiplier from s_screen_width, so it only needs to multiply by
     80 instead of 40.
   - if zp_screencolumn holds the byte offset (column * 2) rather than the
     column, the store sites stop caring. What then has to change is the
     comparisons against the screen width, the increments (+2, not +1), and
     the few places that convert to and from a real column: s_plot,
     cursor_column, s_window_left_edge / s_window_right_edge.
   Do it behind a build flag so the existing MEGA65 build keeps working while
   this lands, and keep it in screenkernal-z6.asm unless the !ifdefs get out of
   hand; on this evidence a whole forked file would be mostly duplication.

   3a. DONE: text at 40x25. -fcm, mirroring -ecm, sets Z6_FCM_MODE. It is
   rejected on any target but the MEGA65, on any version but 6, and alongside
   -ecm. testz6 under -fcm is now character for character identical to the C64
   at 40 columns, and the colour rectangle matches too. The C64, C64 -ecm,
   Plus/4 and plain 80 column MEGA65 builds are unchanged.

   What the design turned out to be:
   - zp_screencolumn stays a column. Only the sites that index the screen
     double it. That leaves the window edges, the margins and every comparison
     alone, and it never escapes screenkernal-z6.asm.
   - zp_colourline is biased by one, so the same doubled index writes the
     character (the even byte of a screen cell) and the colour (the odd byte of
     a colour cell). A row starts at a multiple of 80, so the bias never
     carries.
   - The other two bytes of every cell, the screen's high byte and the colour's
     flags, must be zero and stay zero. init_mega65 clears both once.
   - Reverse video still works: the C64 charset's codes 128-255 are the
     reversed glyphs, so ora #$80 does the right thing when CHARPTR points at
     it. No need for the ECM compromise.
   - CHARPTR points at $2d000, the C64 font in the MEGA65's ROM. Bank 1 is
     therefore entirely free for tiles after all, and the 2 KB reservation the
     plan above assumed is not needed. Revisit for CUSTOM_FONT.

   Three traps, all of which produced a screen that looked nearly right:
   - Most text does not go through s_printchar. It goes through
     print_line_from_buffer in screen-z6.asm, which writes the screen directly.
     Miss that and the text lands one byte per cell.
   - The MORE prompt's cell address is computed from zp_screencolumn as a byte
     offset (.set_more_prompt_pos, and the SCREEN_WIDTH*SCREEN_HEIGHT-1 in the
     .more_access defaults).
   - .s_scroll advances a row with "adc s_screen_width", which is the row's
     byte count on every other target but half of it here.

   Still to do for the screen layer: erase_window and scroll_window were only
   exercised through testz6; the cursor, delete and s_erase_line_from_cursor
   paths are converted but barely tested. Nothing sets a per window background
   colour yet, which is the whole point of FCM for text, and is what retires
   ECM on this target.

   The charset goes at $10000, the bottom 2 KB of bank 1, with the tile store
   from $10800 up. FCLRLO is off, so codes below 256 fetch 8 byte glyphs from
   CHARPTR, and CHARPTR has to point at RAM the VIC-IV can read. Bank 1 is that
   RAM, we own it, and 2 KB out of 64 leaves 62 KB, which still holds the worst
   deduped picture (46.9 KB) with room. The prototype copies the charset out of
   the C64 character ROM, which appears at $d000 while CHAREN (bit 2 of $01) is
   clear; the real build should do the same, or honour CUSTOM_FONT.

4. Graphics. The drawing is not the hard part.

   4a. DONE: Ozmoo draws real pictures on the MEGA65, out of attic RAM.
   `ruby make.rb -t:mega65 -fcm -pics tools/testpics testz6.z6`. The pictures in
   tools/testpics are ours, generated by tools/gen_testpics.py; testz6 draws
   them. Without -pics the build still writes the "pic:N" notes.

   The shape of it, which is the same shape Arthur will need:
   - tools/pics2asm.py writes one p<nnn>.bin per picture and a small index that
     Ozmoo assembles in. make.rb puts the files on the d81 next to zcode, and
     pic_load_all preloads them into attic RAM at $08300000 at boot, using
     m65_load_file_to_reu, exactly as sound.asm preloads the WAVs. Nothing but
     the index and the picture numbers is embedded in the interpreter.
   - A picture file is: cells wide, cells high, tile count, a 48 byte palette,
     a cell map of two bytes a cell, then the tiles at 64 bytes each.
   - Drawing reads the header and palette straight from attic, allocates the
     window a run of the tile store, copies the tiles down into bank 1, and
     fills the cells. A cell's screen code is its tile's address / 64, so it is
     $0400 + slot + index.
   - The palette bank is the window's, not the picture's: a window holds at most
     one picture, so eight banks of 16 above the 16 text colours are enough, and
     the bank is 16 + 16 * window. There is therefore no limit on how many
     pictures a game may have.
   - Pixel indices are stored relative to entry 16, so the tile copy adds
     16 * window as it goes. The DMA engine cannot add, so that one copy is done
     by the CPU. A pixel of 0 is transparent in every bank and is left alone.
   - Each window keeps the run of the tile store it was given, and reuses it
     when the next picture fits. When the store runs out the allocator starts
     again at the bottom, which can only spoil a picture in another window.
   - Every place Ozmoo writes a character also zeroes the cell's high byte (the
     clear_cell_high_byte macro). Without it, text printed over a picture leaves
     the cell pointing at a tile, and erase_picture's spaces do nothing. That is
     the fourth bug of exactly that shape the two-byte cell has caused.

   Two traps worth remembering:
   - make.rb upper-cases the names it puts in the disk directory, so the
     interpreter must ask for "P004", not "p004". A wrong name does not fail
     loudly: kernal OPEN reports no error, the read returns nothing, and one
     page of whatever was in the copy buffer lands in attic RAM.
   - testz6 originally drew all three pictures into window 1, which breaks the
     one-picture-per-window rule and left only the last picture's palette in the
     bank. It now draws picture 4 in window 0.

   4c. DONE: Arthur's pictures fit on a d81, and Arthur draws them.
   `make arthur-pics-mega65` leaves 28 blocks free, and the churchyard picture appears
   above the text. `make z6-pics` does the same for testz6 and the pictures in
   tools/testpics, which are ours.

   Two things were needed, and RLE alone was not enough:
   - Four bits a pixel. A picture has at most 15 colours (index 0 is
     transparent), so attic and the disk hold two pixels a byte and the tile
     copy expands them, which it can do for nothing because it already walks
     every byte to add the window's palette offset. This halves the set before
     it is compressed: 1046 KB of tiles becomes 545 KB.
   - PackBits RLE, not png2fci's scheme. A token of 0..127 means that many plus
     one literal bytes follow; 129..255 means the next byte repeats 257-token
     times. It needs no lookahead, which keeps the 6502 decoder to about thirty
     lines, and it is decompressed straight into attic as the file is read.
   Together: 545 KB -> 484 KB, and 484 + 263 KB of story = 747 KB against the
   d81's 802 KB. RLE alone on 8 bit pixels gives 746 KB of pictures, which does
   not fit; four bit pixels alone give 544 KB, which also does not fit.

   One trap: .pic_find counted its table down with `ldy #picture_count - 1` and
   `bpl`. With 137 pictures that starts at $88, which is already negative, so
   the loop compared one entry and gave up. It worked perfectly for the three
   test pictures. Count up.
   - The palette is per picture, not per set, and each picture carries its own
     16 colours. The measurements that settled that are in the git history: the
     137 PNGs hold 110 distinct palettes of at most 14 colours, and forcing them
     onto one palette is measurably lossy.
   - picture_data must start reporting real sizes and branching true, and
     z_init must stop clearing the "pictures available" bit in header_flags_2
     (see "and #(255 - 8 - 32) ; pictures and mouse never available"). Both have
     to change together, and that is what flips Arthur onto code paths no
     interpreter of ours has ever run. Expect a second round of the sort of bug
     the Z7PLUS/Z6PLUS mix-up caused: the C64 and the MEGA65 will no longer be
     playing the same game.
   - erase_picture blanks the picture's rectangle with spaces. It should
     arguably restore the window's background instead, once windows have one.
   - Nothing sets a per window background colour yet, which is the remaining
     half of step 3 and the reason FCM beats ECM for text.

When the MEGA65 work does start, this is the VIC-IV setup from the old
screenmodel-z6.asm skeleton (deleted; see git history, a7e3b56). It was never
called - the "jmp -" at the end shows how far it got - but the register names
and the full colour / 16 bit character mode setup are the starting point for
giving each window its own background colour.

    ; MEGA65 registers
    VIC2CTRL    = $d016
    VIC3CTRL    = $d031
    VIC4CTRL    = $d054
    LINESTEP_LO = $d058
    LINESTEP_HI = $d059
    COLPTR_LO   = $d064
    COLPTR_HI   = $d065
    HOTREG      = $d05d
    CHRCOUNT    = $d05e
    SCNPTR_0    = $d060
    SCNPTR_1    = $d061
    SCNPTR_2    = $d062
    SCNPTR_3    = $d063

    init_mega65
        ; set 40MHz CPU
        lda #65
        sta 0
        ;  set default colors
        lda #$00
        sta $d020
        sta $d021
        ; enable VIC-II/VIC-III hot registers
        jsr mega65io
        ; enable full color and 16 character mode
        lda VIC4CTRL
        ora #$04 ; full color mode
        ora #$01 ; 16 bit character mode
        sta VIC4CTRL
        ; enable H640, V400
        lda VIC3CTRL
        ora #$80 ; 640 pixel width
        ora #$08 ; 400 pixel height
        sta VIC3CTRL
        ; shift one pixel right (VIC-III bug)
        lda  VIC2CTRL
        ora #$01
        sta VIC2CTRL
        ; Set colour RAM offset to 0
        lda #$00
        sta COLPTR_LO
        lda #$00
        ;lda #$10 ; move colour RAM because of stupid CBDOS himem usage
        sta COLPTR_HI
        ; set characters/line
        lda #$80
        sta CHRCOUNT
        ; set linestep (2 screen bytes = 1 character, so 2*CHRCOUNT)
        lda #$a0
        sta LINESTEP_LO
        lda #$00
        sta LINESTEP_HI
        ; Set screen at $12000
        lda #$00
        sta SCNPTR_0
        lda #$20
        sta SCNPTR_1
        lda #$01
        sta SCNPTR_2
        lda #$00
        sta SCNPTR_3

        ; init screen memory
        +dma_fill $12000, 32, 4000, 2
        ; init color memory
        +dma_fill $ff80000, 0, 8000, 1

        ; Put red C in top corner
        +dma_fill $12000, $43, 1, 1
        +dma_fill $ff80000, 2, 2, 1

        ; disable VIC-II/VIC-III hot registers
        lda HOTREG
        and #$7f
        sta HOTREG

    -   jmp -
        rts

An autoboot sector for the C128 disks. Not a bug, and not urgent - noted only
because starting a game on the 80 column screen is currently a nuisance. VICE
cannot autostart a disk with the 80 column screen selected: its autostart types
LOAD"...",8 and then watches the VIC-II screen at $0400 for the READY prompt,
which never comes when the console is the VDC, so it sits at the load prompt for
ever while the characters it typed land on the VDC. Hence make arthur-c128-80
only attaches the disk and the player types RUN"STORY", as the player manual
already says. The C128 can boot a disk by itself, though, from an autoboot
sector, and a disk carrying one would start in either screen mode with no typing
and no autostart involved - on real hardware as well as in VICE. The catch is
that the boot sector wants track 1 sector 0, which is where Ozmoo already keeps
its config blocks, so it needs a proper look at the disk layout rather than a
quick patch.
