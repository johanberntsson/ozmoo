Known bugs
----------
(none known that stop a v6 game from starting)

Scrollback and extended sound share $40000 on the MEGA65. scrollback.asm:10
puts the scrollback screen RAM at $00040000 and writes 4000 bytes there, while
sound.asm DMAs the current sound effect to bank 4 offset 0, up to 64 KB. The
techreport's memory map lists both, so the map is right and the code is wrong:
opening scrollback while a sound is playing corrupts the first 4000 bytes of
the sample. It heals itself, because the next @sound_effect re-copies the
sample from attic. Not a documentation mistake. Unclear whether it can be
provoked in a real game; nothing in z6 depends on the answer, but the fast RAM
budget below does depend on $40000-$4ffff staying spoken for.

Fixed: Arthur used to crash on startup, before a single Z-machine instruction
was executed. The cause was that v6 was lumped in with v4/v5 rather than with
v7/v8 in the assembly. make.rb has always treated v6 as a "large" version
(story files up to 512 KB, header file length divided by 8, two high bits of
the block address), using "$zcode_version > 5"; the assembly used the Z7PLUS
flag, which only covers v7 and v8. The damage:
  - disk.asm reserved no space at all for disk_info, so the disk_info the
    boot loader copied in landed on top of the readblocks/readblock code.
    Any v6 game that had to page in a block from disk therefore jumped into
    disk_info as if it were code. Arthur hit this on its very first
    instruction, because its "main" routine unpacks to $010c0c, outside the
    resident part of the story file.
  - vmem.asm gave v6 a vmem_highbyte_mask of $01, not the $03 make.rb had
    already used when building the vmap, so block addresses above $20000
    were misread and the age bits overlapped the address bits.
  - the header file length was multiplied by 4 instead of 8, so Ozmoo thought
    every v6 game was half its real size.
The fix was to use Z6PLUS instead of Z7PLUS at every one of these size
related sites. Z7PLUS is now unused, but is still defined.

Still to do for z6 (not crashes):
- These machines will never draw pictures. draw_picture writes a "pic:N" note
  where the picture belongs instead, straight to the screen so that it stays
  out of the transcript, and without moving the game's cursor. erase_picture
  paints over a note of the same width. Both trust the game's y,x (or the
  cursor when either is zero), so a note lands where a picture would have,
  but nothing knows how large the real picture was.
- picture_data never branches, since no picture number is ever valid, and
  reports zero pictures and release 0 for picture 0. picture_table is a
  caching hint with nothing to cache, and make_menu branches false: both are
  correct as they stand, not stubs.
- read_mouse always reports the top left corner and no buttons, and
  mouse_window does nothing. There is no mouse.
- scroll_window scrolls whole character cells, because the header tells the
  game a character is one unit wide and one high. It ignores the scroll delay
  and smooth scrolling that .s_scroll has to honour.
- set_margins is now used for word wrapping, and erasing a window puts the
  cursor on the left margin. The margins do not clip set_cursor, erase_line,
  erase_window or scroll_window, which all still work on the whole window,
  as the spec intends.
- print_form is fully implemented: it is a text opcode, not a graphics one.

Z6 on other targets
-------------------
The C64 came first and it works. The MEGA65 is next. The C128 and the X16 are
still deliberately untouched, so the following are known and accepted, not
oversights:
- The window-local scrolling in screenkernal-z6.asm only covers the code path
  the C64, Plus/4 and MEGA65 share (.s_scroll, and the new s_scroll_window).
  The C128 80 column routine (.s_scroll_vdc) and the X16 routine
  (.s_scroll_vera) still scroll the whole screen, so a z6 window there will
  smear the rest of the display.
- ECM (-ecm) is C64 only, and make.rb rejects it elsewhere. The MEGA65 and X16
  don't need it: their video chips give every character its own background
  colour, so those targets should set the window's background directly rather
  than borrowing the ECM approach.


The plan for z6 on the MEGA65
-----------------------------
The C64 and the Plus/4 will never draw pictures, and keep the "pic:N" notes
whatever happens below.

Screen size, and why 320x200
  Arthur was an Amiga game at 320x200, and z6games/arthur-graphics is scaled to
  that: all 137 pictures fit, the largest being 292x196. So the MEGA65 z6 screen
  is 320x200 in FCM with 16 bit character codes: 8x8 cells, 40x25 of them.

  That is not only the natural fit for the art, it is the only size that fits in
  memory. An FCM cell needs 64 bytes of character data, so a worst case full
  screen picture is 1000 x 64 = 62.5 KB of tiles. At 640x400 it would be 80x50 =
  4000 cells = 250 KB, and there is nowhere to put that. Screen RAM (2000 bytes)
  and colour RAM (2000 bytes) at 40x25 with two bytes per cell are exactly the
  sizes the current 80x25 8 bit mode already uses, so neither grows.

  Fast RAM is 384 KB, and the techreport's map spends most of it: $00000-$0ffff
  interpreter, $20000-$3ffff ROM, $40000-$4ffff sound effect, $50000-$5ffff undo.
  That leaves bank 1, $10000-$1ffff, 64 KB, unclaimed. 62.5 KB of tiles fit there
  with 1.5 KB to spare, so sound and undo both survive and nothing has to be
  sacrificed. It is knife-edge, and it assumes two things that step 2 has to
  confirm: that C64 mode really leaves bank 1 alone, and that the text charset
  can live outside those 64 KB, as ordinary 8 byte glyphs for chars 0-255 with
  full colour only for chars 256 and up (what the VIC-IV's FCLRLO/FCLRHI split is
  for). There is no room for double buffering. If it does not fit, free
  $40000-$4ffff by dropping sound before giving up any of the above: z6 games do
  not use extended sound.

  8 bits per pixel, not the 4 of NCM, even though no picture uses more than 14
  colours and NCM would halve every figure here. An NCM cell is 16 pixels wide
  and a pixel is a nybble, so a picture at an odd x needs a nybble shift, which
  the DMA engine cannot do and which lands us back in CPU side bitmap shifting.
  At 8bpp a pixel is a byte, any x offset is a byte offset, and m65_run_dma blits
  it directly. Revisit only if memory forces it, or if step 2 shows Arthur's
  draw_picture coordinates are always cell aligned.

  Dropping to 40 columns is right for v6 and wrong for everything else, so this
  is a Z6-conditional fork of the MEGA65 constants, not the new MEGA65 default.
  constants.asm sets SCREEN_WIDTH = 80 for the target unconditionally today.

1. Check what already works with -t:mega65. A first pass says: a lot. A
   headless xemu run of testz6 (see CLAUDE.md) shows the window model, the
   margins, print_form and picture_data all behaving at 80x25. But the run
   stopped at a MORE prompt, so draw_picture and scroll_window were never
   reached, and scroll_window is the one new routine with MEGA65-specific
   colour2k/colour1k banking that has never actually run. Cover those two
   first. Check -t:plus4 the same way while there.

2. Before rewriting the screen layer, prototype one hardcoded picture: blit it
   with the DMA engine (m65_run_dma and dma_list already exist in disk.asm)
   into a full colour, 16 bit character mode screen. This is throwaway code.
   It exists to answer the questions that decide the shape of step 3 - how
   many unique tiles a picture costs, where the pixel data lives, and whether
   DMA can do the scrolling too. Freezing a screenkernal around byte copy
   loops and then discovering it needs a DMA blitter would be the wrong order.

3. Rewrite the MEGA65 z6 screen mode to use FCM (full colour mode, VIC-IV,
   with 16 bit character codes) at 320x200, 40x25 cells, as argued above. It
   is needed either way: it gives every
   character its own background colour, which retires the ECM approach on this
   target, and 16 bit character codes are the only sane way to get enough
   unique tiles for pictures. Expect it to touch update_screenpos, s_printchar,
   s_delete_cursor, erase_line, the cursor, and both scroll paths, since a cell
   becomes two bytes. If that turns into a mass of !ifdefs inside
   screenkernal-z6.asm, split it out into screenkernal-mega65-z6.asm, the way
   constants-c128.asm is split out. Decide once the size of the change is known.

4. Graphics. The drawing is not the hard part.
   - The conversion of the picture files belongs in a separate script, not in
     make.rb, which is large enough already. Arthur's 137 PNGs are in
     z6games/arthur-graphics (not in git; not ours to distribute).
   - One palette for the whole set. The originals shared a single 16 or 32
     colour palette; the 622 distinct colours across the PNGs today are an
     artifact of the conversion to PNG, and no single picture has more than 14.
     So the script makes two passes: survey every file to settle on one common
     palette, then force every picture onto it. The palette ships on the d81
     alongside the FCM files.
   - The pictures live in attic RAM. Everything from $8300000 up is free, 5 MB
     of it, against 1,125,824 pixels = 1.1 MB for the whole set at 8bpp. So a
     "pics" file preloaded into attic at boot, exactly the way zcode and the
     WAVs already are, then DMA from attic into the tile store on draw_picture.
     No disk access during play, and almost no new machinery.
   - The binding constraint is the d81, not memory. 800 KB per disk, ~802 KB
     usable, of which Arthur is 263 KB. The full picture set at 8bpp does not
     fit. Start with a handful of pictures that do, get them on screen, and add
     simple compression (the art is flat shaded line art; RLE should crush it,
     and it can decompress into attic at boot) only once it is needed. A second
     disk is the fallback; arthur-d2 already has the shape for it.
   - picture_data must start reporting real sizes and branching true, and
     z_init must stop clearing the "pictures available" bit in header_flags_2
     (see "and #(255 - 8 - 32) ; pictures and mouse never available"). That
     flips Arthur onto code paths no interpreter of ours has ever run. Expect a
     second round of the sort of bug the Z7PLUS/Z6PLUS mix-up caused: the C64
     and the MEGA65 will no longer be playing the same game.


When the MEGA65 work does start, this is the VIC-IV setup from the old
screenmodel-z6.asm skeleton (deleted; see git history, a7e3b56). It was never
called - the "jmp -" at the end shows how far it got - but the register names
and the full colour / 16 bit character mode setup are the starting point for
giving each window its own background colour.

    ; MEGA65 registers
    VIC2CTRL    = $d016
    VIC3CTRL    = $d031
    VIC4CTRL    = $d054
    LINESTEP_LO = $d058
    LINESTEP_HI = $d059
    COLPTR_LO   = $d064
    COLPTR_HI   = $d065
    HOTREG      = $d05d
    CHRCOUNT    = $d05e
    SCNPTR_0    = $d060
    SCNPTR_1    = $d061
    SCNPTR_2    = $d062
    SCNPTR_3    = $d063

    init_mega65
        ; set 40MHz CPU
        lda #65
        sta 0
        ;  set default colors
        lda #$00
        sta $d020
        sta $d021
        ; enable VIC-II/VIC-III hot registers
        jsr mega65io
        ; enable full color and 16 character mode
        lda VIC4CTRL
        ora #$04 ; full color mode
        ora #$01 ; 16 bit character mode
        sta VIC4CTRL
        ; enable H640, V400
        lda VIC3CTRL
        ora #$80 ; 640 pixel width
        ora #$08 ; 400 pixel height
        sta VIC3CTRL
        ; shift one pixel right (VIC-III bug)
        lda  VIC2CTRL
        ora #$01
        sta VIC2CTRL
        ; Set colour RAM offset to 0
        lda #$00
        sta COLPTR_LO
        lda #$00
        ;lda #$10 ; move colour RAM because of stupid CBDOS himem usage
        sta COLPTR_HI
        ; set characters/line
        lda #$80
        sta CHRCOUNT
        ; set linestep (2 screen bytes = 1 character, so 2*CHRCOUNT)
        lda #$a0
        sta LINESTEP_LO
        lda #$00
        sta LINESTEP_HI
        ; Set screen at $12000
        lda #$00
        sta SCNPTR_0
        lda #$20
        sta SCNPTR_1
        lda #$01
        sta SCNPTR_2
        lda #$00
        sta SCNPTR_3

        ; init screen memory
        +dma_fill $12000, 32, 4000, 2
        ; init color memory
        +dma_fill $ff80000, 0, 8000, 1

        ; Put red C in top corner
        +dma_fill $12000, $43, 1, 1
        +dma_fill $ff80000, 2, 2, 1

        ; disable VIC-II/VIC-III hot registers
        lda HOTREG
        and #$7f
        sta HOTREG

    -   jmp -
        rts

Ideas for tasks / subprojects to do next
----------------------------------------
Handle case where REU is present but not large enough to hold entire game.

Verify that game data was written correctly to REU and signal error if not.

Keep everything in residential memory area in RAM rather than just the dynamic RAM. Decrease residential area as needed to make a game fit.

Support REU for fast memory copying.

Add fast-loader code.

Investigate if we can keep channels open between two consecutive block reads, and if this would make the game faster.

If and when we keep channel open between block reads, investigate best interleave value again.

Handle disk errors (To see how it works now: use True Drive Emulation, type "save", detach all disks and try to go through with the save. The game locks up.) The question is how many bytes we are prepared to use on code to handle disk errors.

Allow user to choose save/restore device, including tape, in non vmem mode. (Is this feasible?)

Build config utility. Could be in same location as Z-machine stack and accessible on boot.

Setup profiling, where we can see how much time is spent in different instructions over a session (Log # of executions and # of timer ticks).

Output transcript to printer support.

Add support to save/restore a memory area. (Do we even need this? Is it feasible?)
