Known bugs
----------
DESIGN / MAJOR REFACTOR: DONE on branch z6-pixel, 2026-07-23/24 - the z6 screen
model counts PIXEL units rather than CHARACTER units, and that is now the
DEFAULT for v6 builds. -pu:0 reverts to character cells; the whole model is one
build flag, Z6_PIXEL_UNITS, which make.rb pushes for v6.

WHAT IT BOUGHT, all measured against sfrotz in the same coordinate space rather
than eyeballed (details under phase 3 below):
  Zork Zero's compass   13 physical pixels off  ->  1 (half an art pixel, the
                                                    finest the screen can hold)
  Shogun's left margin  3 columns off           ->  exact
  Arthur's map          connectors 6 px short of the room boxes, and leaving
                        them off-centre         ->  touching, on both axes
The Shogun one was not on the list of known instances when this started, so
assume there are others nobody has looked for.

BRANCH: this work is on z6-pixel, branched from z6. z6 itself stays as it is,
working, so the two models can be compared side by side. Nothing merges back
without Johan's say-so, and z6 must keep building.

Below: the problem, the two originally confirmed instances, the corrected
geometry model, and the staged plan as it was carried out.

THE PROBLEM (as it was; -pu:0 still behaves this way)
Ozmoo counted screen units in whole character cells: it reports the screen as
80x25 chars, font size (property 13) as 1x1, and picture_data in cells. This is a
deliberate simplification ("a v6 unit is a character cell here and a real pixel
in sfrotz" - see the unit bullet in CLAUDE.md and the sfrotz-visual-reference
memory). The v6 games compute picture positions from these reported sizes, so
their maths happens in cells and every picture snaps to the 8-px cell grid. Any
sub-cell offset the game intends is silently lost. sfrotz keeps everything in
pixels, so it places the same pictures exactly.

TWO CONFIRMED INSTANCES (both identical on MEGA65 and X16 - the cause is the
shared screen-z6 layer, not the target picture engines):
1. Zork Zero compass rose (banquet hall / status banner). COSMETIC. The active
   w/e/s and blocked-n indicators sit ~5 px (about half a char) too far RIGHT and
   slightly down. It is ONE 45x40-px overlay picture drawn 8 times at a single
   cell coord (from a live DEBUG_SCREENLOG dump: draw_picture pic 17/10/11/20/13/
   22/15/24, all at win 1, y=1, x=37); the arrows are positioned INSIDE the
   overlay art, so there is NO per-arrow rounding - it is the whole picture that
   snaps. Measured (S down-arrow shaft vs the rose centre, which is baked into the
   320x34 pic 5 at (1,1) and lands identically in both): sfrotz +5.5, x16 +10.5 =
   ~5 px = ~0.6 cell. Reproduce on zorkzero-pics-x16; the compass draws at boot.
2. Arthur online map (press F2 in game; z6games/arthur-map-{sfrotz,x16}.png).
   FUNCTIONAL, not just cosmetic: the room boxes and the connecting segments no
   longer touch, and the map graph reads as broken. Same root cause as (1) but it
   degrades a real feature, which is what tips this from "cosmetic, leave it" to
   "worth the refactor".
   The exact arithmetic, read off txd (routines 187ec / 1892c / 18da4 / 18e68 and
   the helpers 18c10 / 18c20) and confirmed by measuring the sfrotz screenshot:
     spacing = picture 107's size   (18 x 18 units, native)
     offset  = picture 105's size   (5 x 5)
     box     = picture 106 or 108   (13 x 13; 13 + 5 = 18 exactly)
     y = (row - 1) * 18 + 1 + 5,  x = (col - 1) * 18 + 1 + 5
   for BOTH the boxes and the connector segments - they share one lattice. NOTE
   this corrects an earlier description here: there are NO half-steps. There is
   no division by 2 anywhere in the map's coordinate arithmetic (every DIV in
   that code is table-record arithmetic, or the /2 that centres the "Mapping is
   not available for this area." message). So there is no odd/even parity
   hazard, and nothing here needs finer than one unit.
   What actually breaks it today is that picture_data is CELL-ROUNDED: the game
   is told the 18-unit spacing is 2 or 3 cells, the 13-unit box is 2 cells and
   the 5-unit connector is 1 cell, so it lays a 24-px lattice under 13-px box
   art and 5-px connector art. The error accumulates along each row and column,
   which is why the connectors drift off the boxes.

CORRECTED GEOMETRY MODEL (settled in discussion)
- Infocom authored these v6 games for a 320x200 PIXEL space. sfrotz's window is
  640x400 = 320x200 doubled 2x on BOTH axes for display (that is why a
  non-Infocom 320x200 game - e.g. Johan's own z6 game - must be run "sfrotz
  --xscale 2 --yscale 2" to show at the same size; sfrotz only auto-doubles the
  four Infocom titles). So 640x400 is sfrotz's DISPLAY, not the logical contract;
  the logical contract is 320x200.
- Therefore the target is to REPORT 320x200 native pixel units (NOT 640x400):
    * screen units (header $22/$24) = 320 x 200
    * font size (prop 13, and the header font w/h) = 4 x 8  (320/80 cols = 4 wide,
      200/25 rows = 8 tall). Non-zero, and 320/4 still = 80 columns, so Arthur's
      divide-by-font-size stays safe.
    * picture_data returns NATIVE art-pixel sizes (compass overlay = 45x40, not
      90x80). This is what the Infocom games AND a portable new game expect, so
      coordinates match sfrotz with NO per-terp conversion - the portability win
      (write once, place identically on Ozmoo and sfrotz).
- Nice consequence of 320x200 (vs the 640x400 first floated in discussion):
  VERTICALLY Ozmoo is already native. The framebuffer is 640x200, so 200 units ->
  200 rows, 1:1 - no vertical SCALING, no vertical precision loss. One native X
  pixel = 2 framebuffer px, which is exactly sfrotz's own granularity (1 source
  px = 2 display px), so matching it is exact, not approximate.
  CORRECTION (2026-07-23): this bullet used to go on to conclude that all the
  sub-cell placement work is therefore HORIZONTAL ONLY. That is wrong, and it
  cost phase 0 half its usefulness. No vertical scaling does NOT mean no
  vertical sub-cell placement: the scale is 1:1, but the placement GRID is still
  a cell, 8 pixel rows tall, on both picture engines. A picture asked for at
  y = 6 needs to start 6 pixel rows into a cell, which neither engine can do.
  Arthur's map needs exactly that - see instance 2 below, whose 18-unit lattice
  puts rows at y = 6, 24, 42, 60, 78, ... i.e. 6, 0, 2, 4 mod 8. So sub-cell
  placement is needed on BOTH axes; see phase 0b in the staged plan.
- SEPARATE issue, do NOT conflate with the above: the framebuffer is 640x200, so
  a picture is doubled horizontally but not vertically and comes out ~2x
  wide/squat vs sfrotz's square doubling (measured on Arthur's rose: W/H ~1.3 on
  x16 vs ~0.9 in sfrotz). Reporting pixels does NOT fix this aspect squash - that
  would need a 640x400 framebuffer (vertical doubling too), a much bigger change
  (tile store, screen mode). AND it may not be a real defect: on real MEGA65/X16
  hardware on a 4:3 display the 200-line screen is stretched vertically, which
  largely cancels the horizontal doubling. VERIFY ON REAL HARDWARE before deciding
  the aspect needs any work; the measurement above is off a square-pixel emulator
  screenshot and probably overstates it.

SCOPE / CONTAINMENT
- z6-only: all in screen-z6.asm / screenkernal-z6.asm / the two picture engines.
  master's character-based model is untouched, so this cannot regress the z3/z5
  games.
- 2-byte X coordinates are needed (0..319 > 255). Y stays one byte (0..199).
- Text NEVER needs sub-pixel placement - games always move the cursor in
  font-size steps, so text stays on the cell grid. Only PICTURES need sub-cell
  placement. So the text engine can stay in cells and convert at the opcode
  boundary (X/4, Y/8); the picture layer carries the horizontal sub-cell
  remainder.

STAGED PLAN (each phase independently useful / verifiable)
Phase 0 - horizontal sub-cell blit (de-risk first, no reporting change): DONE
  2026-07-23, commit "Pixel refactor phase 0: place X16 pictures at any art
  pixel". The X16 boundary-tile bake takes an arbitrary art-pixel (2-physical-px)
  horizontal offset instead of the fixed half-cell an odd text column asks for.
  .pic_place_cursor computes .pic_px, the picture's left edge in 320-wide art
  pixels (still just column * 4 - nothing reports pixels yet), and .pic_map_x
  splits it into the first layer 0 map column and the bake's .pic_shift.
  What phase 1 has to know about it:
  - .pic_shift is 8 - (px mod 8), NOT px mod 8. The bake reads forward (buf byte
    j is source byte j + shift), so a bigger shift moves the picture LEFT, while
    a bigger remainder means it starts further right inside the tile. 4 is its
    own complement, so the old half-cell case cannot tell the two conventions
    apart - the inverted version rendered perfectly until an offset that was not
    half a cell was tried. Do not "simplify" this.
  - A boundary cell's two TEXT cells no longer take one source art cell each: at
    any shift but 4 one of them straddles both. .pic_boundary_masks works that
    out once per picture into .bd_lmask/.bd_rmask for .pfo_blank_text.
  - .pic_gc's incoming rectangle now comes from .pic_lx/.pic_cw/.pic_shift; the
    old text-column arithmetic only agreed at shifts 0 and 4.
  - Testing: 'Z6_PIC_XSUB=n' in make.rb's $GENERALFLAGS (a flag entry may now
    carry its own value) shifts every picture n art pixels, positive or
    negative. testz6 draws picture 4 a second time at an odd column so the
    boundary path runs without playing a commercial game to a scene. Verified by
    dumping VRAM from x16 testz6 and rendering layer 0: no offset is
    pixel-identical to the pre-refactor engine, odd column included, and
    XSUB 1/2/3 move both the aligned and the odd-column picture exactly 2
    physical pixels per art pixel with their colour runs intact - between the
    two pictures that covers every shift 0..7.
  Not done in phase 0, and still open: the plan called for gating on picture
  size, because every boundary cell is a freshly baked un-deduped tile (the same
  store pressure behind the tile-store wrap bug). The existing .dp_odd_fits
  check still applies unchanged - a picture too big falls back to grid-aligned
  placement - so a big picture degrades rather than corrupts, but nothing new
  was added for the arbitrary-offset case, and the "accounting for baked tiles"
  item further down this file is the proper fix.
  Also not done: the compass was NOT made to line up. That was the plan's
  suggested phase 0 test, but with the screen model still reporting cells the
  game asks for a cell column, so the offset needed is not a sub-cell remainder
  of the same number - it only becomes one once phase 1 flips the reporting.
  The blit was verified against measured offsets on testz6 instead.
Phase 0b - SUB-CELL PLACEMENT ON BOTH AXES, generated from staging: DONE
  2026-07-23, commit "Phase 0b: generate off-grid picture cells from staging, on
  both axes". The X16 engine builds the cells a picture covers straight from the
  staged picture data and never copies its unshifted run into the store, which
  is what made the vertical axis affordable; the boundary bake phase 0 added is
  gone with it. It was needed because Arthur's map lattice is 18 art pixels, so
  its rows land 2, 4 or 6 pixels into a cell (see instance 2 above) - vertical
  sub-cell placement is not optional, and the geometry model's claim that all
  the work was horizontal was wrong.
  The costing that chose this over a second bake path (tools/tilebudget.py, all
  four games; the store is 1023 tiles):
    bake, horizontal (what phase 0 did)  max 1605-1711   over in 21 pictures
    bake, both axes                      max 1640-1752   over in 22
    generate from staging                max 1025-1066   over in 12
    ...plus a runtime dedup              max  676- 832   over in none
  The dozen still over are 40x25 full-screen pictures, which every game draws at
  the origin and never shifts; .pic_gen_size falls those back to the tile grid.
  Runtime dedup is unbuilt headroom - it needs a hash table to avoid an O(n^2)
  compare and nothing needs it.
  What it left standing from phase 0: .pic_px (now with .pic_py beside it),
  .pic_map_pos, the Z6_PIC_XSUB test hook (Z6_PIC_YSUB joins it) and the
  VRAM-dump/render verification harness. What it removed: .pic_bake_boundary_buf,
  .pic_fill_cells_odd, .pic_boundary_masks, .dp_odd_fits, and the 8 - r shift
  convention - .pic_shift is now the natural remainder, because .gen_tile
  addresses source pixels directly instead of reading forward from a tile.
  THE BUG THIS TURNED UP, worth remembering because it is a class and not a
  typo: .pic_alloc reused a window's tile run whenever the SAME PICTURE was
  redrawn into it. That was sound for as long as a run held the picture's own
  tiles wherever it was put - rewriting it changed nothing. A generated run is
  only correct at the position it was generated for, so redrawing the same
  picture at a different offset rewrote the tiles the first placement's cells
  were still pointing at. Reuse now also requires the placement to match
  (pic_win_shift, .pa_pack_shift). Generalise: when a cache key stops covering
  everything the cached thing depends on, the failure is silent corruption of
  something drawn earlier, somewhere else on the screen.
  It also retires the "account for baked tiles" item further down this file:
  the cell count is known before the draw, so .pic_alloc reserves it exactly and
  nothing is allocated mid-draw any more.
  Verified: on x16 testz6, aligned placement is pixel-identical to the
  pre-refactor engine (odd column included), Z6_PIC_XSUB 2 and 3 move a picture
  exactly 2 physical pixels per art pixel, Z6_PIC_YSUB 1, 3 and 7 exactly one
  row per unit, and (3, 5) does both at once. On the real thing, Arthur's first
  room on the X16 - recolouring frame, scene composited inside it, the
  tile-store allocator - renders pixel-identical to the pre-refactor build on
  both the picture and the text layer.
  STILL TO DO here: the MEGA65 engine has none of this (phase 4). .pic_gc's
  rectangle is dealt with below.
  THE SECOND BUG THIS TURNED UP, found in play-testing 2026-07-24 and FIXED:
  the bottom two rows of Arthur's full-screen intro pictures came out as a band
  of screen background with stray pixels scattered through it, across the
  frame's lower border (z6games/arthur-x16.png). MEGA65 was fine. It was
  .pic_seek, the one primitive phase 0b added: it adds a 16-bit byte offset to
  .gen_base, which sits at $a000 in an 8 KB bank, and the sum overflows $ffff
  with the carry going nowhere - the bank is a separate byte, and the cmp #$c0
  normalisation loop cannot recognise a WRAPPED address as too high. So every
  tile past index ($ffff - .gen_tiles) / 32 was read out of low memory in the
  wrong bank. The offset is now split into whole banks and a remainder before
  it is added. Notes worth keeping:
  - Only pictures whose file runs past ~24.5 KB reach the boundary, and only
    down the generated path, so nothing could show this until phase 1 made real
    off-grid offsets appear. In Arthur's set it is [P002] and [P084]; the
    threshold is a picture file over 24576 bytes.
  - The MEGA65's .pic_seek is the same routine over flat attic RAM, where the
    carry just goes into the third byte, which is why that engine was clean.
  - It looked exactly like an allocator or compositing fault - a strip of the
    frame destroyed, like the tile-store wrap - and was neither. What settled
    it in one step was rendering the layer 0 map out of an x16emu -dump V
    capture and diffing it cell by cell against the [P###] file: 58 wrong
    cells, every one of them needing a source tile index >= 710, and every cell
    below that pixel-exact. Predicted threshold and measured threshold agreed.
  TWO MORE FIXED WITH IT, both latent, both found by reading the allocator
  while chasing the above:
  - .pa_reset fell into .pa_pack_shift instead of .pa_place, because phase 0b
    inserted the helper between them. A .pic_alloc that ran out of store even
    after compacting therefore returned WITHOUT PLACING: .pic_slot still held
    the last picture's run, so the new picture's tiles were written over one
    the screen was showing, the window's bookkeeping was stale, and
    pic_next_tile was left at the bottom of the store. The allocator is a chain
    of fall-throughs; the helper now lives outside it, as the MEGA65's does.
  - .pic_gc treated a vertically shifted picture's TOP edge row as interior:
    the x axis had inc .gc_x0 and the y axis had nothing. A tile shown only by
    cells in that shared row could be reclaimed while the draw still needed it
    to composite against. .gc_y0 now mirrors .gc_x0. (The MEGA65's .pic_gc has
    no shift adjustment on either axis and should get the same treatment - it
    has 2048 tiles and compacts far less often, so nothing has surfaced.)

Phase 1 - report pixel units behind a build flag: DONE 2026-07-23, commits
  "Phase 1, part 1: report art pixels behind Z6_PIXEL_UNITS" and "part 2: finish
  the pixel-unit conversions". The flag is Z6_PIXEL_UNITS; Z6_UNIT_W /
  Z6_UNIT_H (screen-z6.asm) are a character cell in art pixels, 4x8 at 80
  columns and 8x8 at 40 where the art is not doubled, and both are 1 without the
  flag so every converted site compiles back to what was there. The x
  conversions are 16-bit: 320 does not fit a byte. Text stays on the cell grid,
  so the text engine keeps counting cells and the opcodes convert at the
  boundary; only pictures carry the remainder, which is what phases 0b and 4
  taught the engines to draw.
  Converted: the header ($22/$24 -> 320x200, $26/$27 -> 8x4, at all three write
  sites); get_wind_prop and put_wind_prop properties 0-7 and 13; set_cursor and
  get_cursor; move_window; window_size; set_margins; erase_line; scroll_window;
  draw_picture / erase_picture via .pic_place_cursor; picture_data; read_mouse
  and the mouse header-extension coordinates; and header word $30.
  picture_data reports NATIVE art-pixel sizes, which needed pics2asm.py to emit
  them (--pixel-units, passed by make.rb when the flag is set, so a normal
  build's pictures.asm is unchanged). Cells * 4 would not do: Zork Zero's
  compass overlay is 45x40 and would round to 48x40 - the snapping this whole
  refactor exists to remove.
  TWO THINGS WORTH REMEMBERING, both found by running rather than reading:
  - Header word $30, the width of text measured through stream 3, is in UNITS
    and is not a coordinate opcode at all. Arthur right-aligns its status line
    by measuring the text and set_cursor'ing to (width - measured), so a count
    left in cells put the line a quarter of the way across the screen. This is
    exactly the "looks unrelated and is not" this plan warned about; assume
    there are more like it, and drive the games rather than auditing the opcode
    list.
  - The X16/C128 header path computes the height at RUN TIME and inherited the
    header offset in y from the preceding write_header_byte. The unit
    conversion clobbers y, so the word landed at $20/$21 and the game was told
    it had 200 columns and 0 rows. An implicit register hand-off across a call
    is invisible until something is inserted between them.
  Verified: a probe game built into Ozmoo reports cols 80 rows 25, units
  320x200, font h 8 w 4, get_wind_prop 13 = 8x4 and picture_data in native
  pixels. Arthur on the X16 boots, draws its frame with the scene composited
  inside it, and lays its status line out correctly - one column left of the
  cell build, which is the sub-cell precision landing. The default build was
  checked BYTE IDENTICAL at each step (assembled x16 testz6 PRG), and the full
  matrix and all five pictures builds pass with the flag both on and off.
  NOT YET DONE, and this is phase 3's work: only Arthur has been driven with the
  flag on, and only into its first room. Zork Zero's compass (the other
  confirmed instance at the top of this file), Arthur's F2 map - the thing that
  motivated the refactor, whose 18-unit lattice should now come out exact - and
  Journey and Shogun all still need checking. Journey and Shogun look unrelated
  and are not: see the $30 note above.

  ARTHUR'S F2 MAP (instance 2): FIXED. This entry previously said REGRESSED,
  with a diagnosis attached; both were WRONG, and the reason is worth keeping.
  The capture behind them was taken while the map was being REDRAWN - the drive
  script pressed F2 twice, and the dump caught the screen with a later picture
  part-way through loading its palette into bank 10. The paper's cells still
  pointed at bank 10, so they rendered against a half-loaded palette and came
  out black. Nothing was wrong with the interpreter. A mid-redraw dump looks
  exactly like a real rendering bug and the tell is a palette bank holding
  another picture's colours in 0..7 and zeros above; check the bank a suspect
  cell uses before believing what it renders as.
  With a clean capture (F2 once) the map is correct, and it is BETTER than the
  cell build in exactly the way instance 2 predicted. Measured on the scan line
  through the room box, which is 13 art pixels = 26 physical across in both:
      cell units    box x 288..313, connector run (320, 329) at y=42
                    -> a 6 px (3 art pixel) GAP, and the connector leaves the
                       box below its centre (box y 32..44, centre 38)
      pixel units   box x 214..239, connector run (238, 249) at y=29
                    -> the connector MERGES with the box's right border, gap 0,
                       and leaves it at the exact vertical centre (box y 23..35)
  So the connectors touch the boxes now, on both axes. That is the functional
  breakage this whole refactor was for.
  The ring diff also settled the other question it was run for: the two builds
  issue the SAME 16 draws in the same order, so the game is not choosing
  different pictures - only their positions differ. The paper (picture 137,
  40x12 art cells) is drawn with no shift at all in both, down the copied path,
  and its 19 tiles and its palette bank are BYTE IDENTICAL between the builds.

  How to drive it: Arthur's mode keys are physical F2 = the map and F3 = the
  inventory (z-codes 134 and 135; the dispatch is at 18353 in txd, on G32).
  F2 needs the emulator window focused - xdotool windowfocus then plain XTEST,
  and the Xvfb lock must be cleared first or the keys go nowhere and you get a
  capture of an undriven boot. That happened twice here; once it produced a
  "pixel units" capture from a cell-units binary, because the game had been
  rebuilt with the flag off in between. ALWAYS rebuild the game after changing
  the flag, and check the build log says so.

  - JOURNEY's title screen and command-menu header are the same in both, with
    the centred lines landing within one column. Fine.
  - TESTZ6 has been rewritten to work in CELLS and convert at the opcode
    boundary, reading the font size from get_wind_prop 13 (commit "testz6:
    work in cells and convert at the opcode boundary"). It scales every
    coordinate and count it passes, and converts values it reads back before
    printing them, so its output is the same under either model - which is
    what a portable v6 game has to do anyway.
    AND IT IMMEDIATELY FOUND A BUG, since FIXED. The fix commit is "Fix a
    self-referential guard that half-flipped the pixel model". Two commits
    earlier, "do not break a z3/z5 build" had introduced Z6_PIXELS by renaming
    every !ifdef Z6_PIXEL_UNITS in ozmoo.asm - including the derivation, which
    became

        !ifdef Z6_PIXELS {
            Z6_PIXELS = 1
        }

    a symbol that tests for itself and so is never defined. Every header
    conversion in ozmoo.asm was compiled out while screen-z6.asm, which keys
    off Z6_PIXEL_UNITS directly, kept converting. The model was half-flipped:
    the header reported CELLS and the opcodes expected UNITS, so a game that
    divides the reported screen size passed values four to eight times too
    small - window 0 became two rows and sat on a MORE prompt for ever.
    Three things worth keeping from it:
    - A blanket rename across a file will rewrite the definition as well as the
      uses. A guard that tests the symbol it defines is silently always false.
    - The failure mode of a HALF-converted unit model is not a wrong layout, it
      is a game that appears to hang, because the geometry collapses rather
      than shifts. If the flag ever looks like it hangs something, check the
      header against get_wind_prop 13 first.
    - The Arthur, Zork Zero, Shogun and Journey results above all predate that
      commit, so they stand.
    testz6 also lays its windows out in cells and converts, rather than
    dividing the reported units: 25 rows / 10 is two cells but 200 pixel rows
    / 10 is two and a half, so the same expression placed the window
    differently under each model. With that it now renders PIXEL-FOR-PIXEL
    IDENTICALLY under both, which is what makes it a regression check for the
    flag rather than a second thing to interpret.

  FIXED along the way: building a z3/z5 game with the flag left on failed to
  assemble at all, because $GENERALFLAGS is global and ozmoo.asm reached for
  constants that only exist in screen-z6.asm. ozmoo.asm now keys off Z6_PIXELS,
  derived only when Z6 is defined. Nothing but running the whole matrix WITH

SETTLED 2026-07-23 - WHAT SFROTZ ACTUALLY REPORTS (this was the first open
question, and the answer contradicts the geometry model above; read this before
starting phase 1). Measured against sfrotz 2.55 (frotz-2.55, the Fedora build,
no config overrides - /etc/frotz.conf is all comments and there is no ~/.frotzrc)
and cross-checked against its source.

  For ALL FOUR Infocom v6 games sfrotz reports:
    screen units (header $22/$24) = 640 x 400
    font (header $26 = HEIGHT, $27 = WIDTH in v6) = 16 tall x 8 wide
    get_wind_prop 13 = 16 x 8 (height high byte, width low byte)
    screen chars/lines ($21/$20) = 80 x 25   (640/8 and 400/16)
    picture_data = the art size DOUBLED on both axes, not native.

  So sfrotz's model is Infocom's 320x200 art space uniformly scaled 2x into a
  640x400 window. It does NOT report 320x200, and its picture_data is not
  native.

  Where that comes from (frotz-2.55 source):
  - src/sdl/sf_resource.c os_init_screen(): screen_width = AcWidth,
    screen_height = AcHeight, font from os_font_data(FIXED_WIDTH_FONT),
    screen_cols/rows = the quotients. AcWidth/AcHeight default to
    DEFAULT_WIDTH/HEIGHT = 640/400 (src/sdl/sf_frotz.h).
  - checkwidths() only ever RAISES that from the blorb's Reso chunk. All four
    games' Reso says 320 x 200 (Arthur, Journey, Shogun, Zork Zero - checked),
    which is below 640x400, so the window stays 640x400.
  - The Infocom-v6 scale is m_v6scale_x/y, "Display / Infocom V6 Scaling X|Y",
    default 2 and 2. The EGA halving next to it only fires when Reso is exactly
    640x200; ours are 320x200, so it does not, and the scale stays 2 x 2.
  - src/sdl/sf_resource.c os_picture_data() returns m_gfxScale_h * height and
    m_gfxScale_w * width - the SAME variables that scale the drawing. So "sfrotz
    doubles the pictures" and "sfrotz doubles picture_data" are one fact, not
    two.
  - None of the reporting has a story-ID branch; only the scale does. A
    non-Infocom v6 game therefore gets 640x400 / 16x8 with NATIVE picture_data
    (scale 1), and "sfrotz --xscale 2 --yscale 2" multiplies m_gfxScale, so it
    doubles picture_data too.

  How it was measured, to redo it: a 15-line v6 probe game that prints $20/$21,
  $22-->0, $24-->0, $26->0, $27->0, get_wind_prop 13 and picture_data for
  pictures 1..60, run under Xvfb and screenshotted ("import -window root"; the
  SDL window is centred in the root, so crop at its -trim offset, not at 0,0).
  Attaching a game's blorb to the PROBE (a non-Infocom story) reports that
  blorb's pictures at scale 1, which is how the native sizes were read off.
  Confirmed against the real thing: Zork Zero's status banner is picture 5,
  native 320 x 34, and in sfrotz it renders 640 wide and exactly 68 rows tall.

  WHAT THIS MEANS FOR THE PLAN. The "CORRECTED GEOMETRY MODEL" above targets
  320x200 / font 4x8 / native picture_data, and justifies it with "coordinates
  match sfrotz with NO per-terp conversion - the portability win". That
  justification is FALSE: sfrotz's numbers are twice ours on both axes. The
  target itself may still be the right one, but it has to be chosen on its own
  merits now. The two candidates:

  DECIDED 2026-07-23 (Johan): report 320x200 - option A. There is no reason to
  copy sfrotz's 640x400; that is just a display scaling, and A is the only one
  exactly reachable on Ozmoo's own grid. The parity worry that option B was
  hedging against turned out not to exist - Arthur's map has no half-steps at
  all (see instance 2), so nothing wanted the finer numbers.

  A. 320x200, font 4x8, native picture_data (the plan as written).
     + Matches Ozmoo's own grid exactly: 1 unit X = 2 physical px (one art
       pixel, the placement granularity phase 0 just built), 1 unit Y = 1 row.
       Every reportable coordinate is exactly reachable.
     + The four Infocom games lay out identically to sfrotz anyway, because
       their maths derives positions from the reported screen/picture/font
       sizes and is therefore scale-invariant.
     - Absolute numbers differ from sfrotz by 2x, so a NEW portable game that
       hardcodes pixel coordinates rather than deriving them lands in the wrong
       place on one of the two.
  B. 640x400, font 8x16, picture_data 2x native (what sfrotz reports).
     + Absolute numbers match sfrotz for the four Infocom games, and for a new
       game run as "sfrotz --xscale 2 --yscale 2".
     - Not exactly reachable: Ozmoo's framebuffer is 640x200 and its art is
       pixel-doubled horizontally, so an odd X unit and an odd Y unit are both
       unrepresentable. NOTE this costs no real precision - the achievable
       granularity is 2 physical px across and 1 row down either way - so B
       buys nothing but bigger numbers and rounding.
     (This was the option the "check Arthur's F2 map half-steps" question was
     about. Answered: there are no half-steps, so B had nothing to buy.)

  TRAP for whichever is chosen: in v6 header byte $26 is the font HEIGHT and
  $27 the font WIDTH - swapped from v5. constants-header.asm names them the v5
  way (header_font_width_units = $26) and ozmoo.asm writes 1 to both, so the
  swap is invisible today and will not be the moment they differ.

STILL OPEN:
- Phase 2 granularity: is a 2-byte cursor X enough, or do we bite the bullet and
  make the per-window arrays pixel too?
- Aspect squash: a real defect on hardware, or masked by the display? Decide
  before committing any 640x400-framebuffer work. (Note the finding above does
  NOT bear on this: sfrotz scales 2x on both axes, so its pixels stay square,
  while Ozmoo's 640x200 framebuffer doubles only across. Reporting B would not
  change that either - it is a framebuffer question, not a units question.)

FIXED (July 2026): in Arthur on the C64 and MEGA65, the LAST character of every
line of a parser message came out as the next screen code up - typing a bad word
gave 'You don't need to use the word "aaaa.#' for the closing quote, and the line
above ended "wore" instead of "word". s_ignore_next_linebreak is a THREE byte
array in the constants*.asm zero page maps, sized for the non-z6 screen model,
with s_reverse immediately after it; z6 has eight windows and indexes it by
current_window, so windows 3-7 wrote past the end - on the C64 window 3 IS
s_reverse (4/5 are s_stored_x/y, 6 is s_current_screenpos_row). Arthur prints
every parser message into window 3 in reverse video, so s_reverse held $80;
.normal_char read that as the window's "ignore next linebreak" flag, took the
sign bit for "set" and INCed it to $81, and the "ora s_reverse" two instructions
later then set bit 0 of the character. Only the last character of a line was hit
because that is the only one s_printchar prints - the rest go through
print_line_from_buffer, which ORs print_buffer2 instead. Fixed by giving z6 its
own eight-byte array outside the zero page; the equates stay under !ifndef Z6, so
non-z6 builds are byte-identical.
The X16 escaped it only by luck: Z6_WINDOW_BG means it never sets s_reverse for
these windows, but its map has the same adjacency ($aa + 3 = $ad) and the same
latent bug. Every other per-window array was audited and is fine - see CLAUDE.md
for what was checked, so it need not be redone.
Diagnosis was by measurement: dump screen RAM for the actual screen code (not a
screenshot), trace exec the OR chain to see which OR introduced the bit, then
trace store on the variable to find who wrote it. Two dead ends on the way, both
mine: a bad log regex said the guilty INC "never executes" (it ran 4808 times),
and a cross-run correlation of char against mask appeared to clear s_reverse.
Correlate in ONE run, and verify a negative before believing it.

FIXED (July 2026): on the X16 pics build, Arthur's frame was destroyed after a
few room changes ("w", "e", "w" was enough) - it filled with fragments of the
room pictures in the wrong colours, permanently, since the frame is drawn once
and never redrawn. Root cause: .pcf_alloc_and_write wrapped pic_next_tile back
to PIC_FIRST_TILE when the store filled. The tiles it bakes (the even path's
composites, the odd path's boundary tiles) are allocated mid-draw and belong to
no window's run - .pic_alloc reserves only the picture's own tiles - so the
store can run out there, and the wrap landed on the frame's tiles at the bottom.
Two things made it bite hard:
- The odd path costs 2x: a picture's copied run (cw*ch, only ever read as the
  bake's source) PLUS its boundary tiles ((cw+1)*ch, what the map points at).
  That drove pic_next_tile to the top of the 1023-tile store within two rooms.
- The wrap then DEFEATED .pic_gc permanently: it left pic_next_tile low, so
  .pic_alloc's fit check always passed and never compacted again. The allocator
  simply marched back up through the frame. This is why the damage appeared two
  turns AFTER the wrap - only when the march reached the frame's tile range.
Measured with counters on a real run (dumps at each turn): pic_next_tile went
698 -> 7 (wrap) -> 343 -> 679, and the frame's tiles lived at 347..697, so the
picture drawn on the fourth turn (tiles 496..657) landed inside it. The wrap was
reached via the EVEN fallback: with pic_next_tile at 1013, .dp_odd_fits
correctly forced a 3x3 icon to even placement, .pic_alloc correctly saw its 9
tiles fit, and then the unguarded composite bake ran off the end.
Fix: .pcf_alloc_and_write no longer wraps. pic_next_tile saturates at
PIC_MAX_TILES and the bake fails with carry clear; callers degrade (the even
paths keep their own un-composited tile, the odd path keeps what is behind).
This is self-correcting: a saturated pic_next_tile fails .pic_alloc's fit check,
so the next picture compacts the store and the bakes have room again.

TODO (X16 pics, option 2): make the store account for baked tiles, so the
degradation above never triggers. .pic_alloc reserves only .pic_ntiles; the
bake needs up to (cw+1)*ch more on the odd path and up to cw*ch on the even
path. Reserving run + worst-case bake up front would make .pic_gc fire at the
right time and keep every cell exact. The catch, and why it was not done as the
bug fix: the worst case is wildly pessimistic for the big pictures. Arthur's
frame is 37x25 = 925 cells and 653 tiles, so a worst-case reservation of ~1578
exceeds the 1023-tile store outright and would trigger spurious .pa_reset calls
on a picture that in practice composites almost nothing. A real fix therefore
needs a TIGHT bake estimate, not a bound - e.g. have pics2asm.py count the
partly-transparent cells per picture (it already classifies cells: it emits
$ffff for fully transparent ones) and assemble that count into the picture
index beside pic_width/pic_height, so the interpreter can reserve exactly what
the bake will use. Note the store cap is a hard VERA limit (a tile map entry is
a 10-bit index), so it cannot simply be raised; and the MEGA65 only gets away
with the same wrap because it has 2048 tiles and half the per-room cost.
Related: the odd path's 2x cost is what fills the store in the first place, so
the staging-read follow-up below (bake boundary tiles straight from the staging
banks, without copying a run first) would relieve the same pressure.

FIXED (July 2026): on the X16 pics build, Zork Zero's in-text insets (the
illuminated drop-cap initials, the banquet-hall statue, the room icons) drew on
a BLACK background inside the white text window, where the MEGA65 and sfrotz
show them on white. Root cause is the two-layer screen: text (layer 1) is
blanked transparent over a picture so layer 0 shows through, and a picture's
transparent pixels (index 0) then reveal the VERA backdrop - palette entry 0,
which is black and is shared with text colour 0, so it cannot be recoloured. On
the MEGA65 there is one layer, so a transparent FCM pixel shows the global $d021
(white). The fix mirrors that: a picture's transparent pixels are filled with
the screen background colour (pictures-x16.asm).
- x16_screen_bg tracks the screen background as the MEGA65's $d021 does: the
  last set_colour background, a VERA colour; set_window does NOT change it. This
  matters because a game draws an inset into a throwaway window (set_window,
  draw, set_window 0 - Zork Zero routine 1330c) whose own background is the
  default, while the surrounding text is another window's white. Using the
  drawing window's own background (the first attempt) filled with the wrong
  colour; the global screen background is right.
- .pic_compute_bg_index finds the index in the picture's palette bank whose
  colour is x16_screen_bg. The insets' palettes have no white (they are reds,
  greens, etc., transparency at index 0), so an exact match usually fails; then
  it INJECTS the screen background into a free index - one the picture's pixels
  do not use, recorded in pic_used while .pic_copy_tiles runs - and points
  transparent pixels there. Only a DIRECT picture's own bank is injected into;
  an adaptive picture shares the direct one's bank and is left alone.
- Both the even and odd "nothing behind" cell paths bake the fill
  (.pcf_bake_bg / .pcf_fill_bg); cells composited over another picture (Arthur's
  scene in its frame) are untouched, and a black screen background or a
  fully-opaque picture changes nothing. Verified in play (Johan): Zork Zero's
  banquet-hall insets now sit on white like the reference. testz6 pics-x16
  still draws its test pictures; Arthur's adaptive frame is skipped by the
  direct-only gate and its full-screen title has no transparent pixels to fill.

DONE: per-pixel compositing. A small picture drawn over a scene - Arthur's

FIXED: the white stripe across Arthur's full-screen intro pictures - and,
almost certainly, the "games drop or change the odd stretch of body text"
bug, which had the same root cause. Not a write into the tile store's banks
at all: the first 2 KB of colour RAM is also mapped at $1f800-$1fffff in bank
1, whose top is CBDOS workspace, so every SD/disk access rewrites colour
bytes around $7f2-$7fb. The 40-column screen's 2000 colour bytes stop just
short of them; the 80-column screen's 4000 reach row 12 cell 57, and the
DOS's $f8 bytes have bit 4 set - a VIC-IV GOTOX token in FCM's 16-bit colour
cells, which blanks the rest of the row from that cell on. Hence a white
stripe over the last fifth of a middle picture row, and text lines losing
their tails "differently on each run" (whenever disk access had scribbled
since the row was last printed). Diagnosed in xemu by dumping the stripe
cells (valid tile codes, garbage colour flag bytes) and then watching
$ff807f0 through the boot: the bytes tick during every disk phase. The fix
moves the screen's colour region off the DOS bytes with the VIC-IV colour
offset ($d064/5): FCM_COLOUR_OFFSET = $0800 (constants.asm), added to
zp_colourline everywhere it is computed; scrollback's temporary colour moved
to $1000 to stay clear of it; quit puts the offset back to 0 for BASIC.
Verified: Arthur's sword-and-chapel and Merlin intro pictures render
pixel-clean, and testz6 still matches dfrotz at both 40 and 80 columns.

FIXED, found on the way: drawing a full-screen picture over another (or
redrawing one over itself, which Arthur's intro does) baked a composite tile
for every cell - ~1850 allocations on a 2048-tile store - wrapping
pic_next_tile into the picture's own run and overwriting source tiles that
later, deduplicated cells still needed. This was the todo entry above coming
true, as garbled borders and bottom band on the intro pictures rather than as
the stripe. .pcf_make_tile now counts the overlay tile's transparent pixels

FIXED: the store (2048 tiles) cannot hold two big pictures at once - Arthur
draws the Merlin scene (1057 tiles) centred over the sword picture (1223),
whose gold frame stays visible - so recycling the sword's tiles showed
garbage around the smaller picture. .pic_alloc now compacts instead of
wrapping (.pic_gc): when a fresh run will not fit, every tile still shown by

of the store in ascending order (a survivor can only move down, so the copy
is safe in place), and its cells repointed; the new run lands above the
survivors. ~500 frame tiles + 1057 fit easily. The rewrite works from a

If v6 scrollback is ever enabled, the picture corruption below must be handled:
entering scrollback repoints the VIC-IV screen ($d060) to $40000
(scrollback.asm .scrollback_screen_ram), which under -pics is the foot of the

pictures are on screen, and leaving restores the pointer but not the tiles.
The tried fix (works, but reverted as untestable dead code while scrollback is

FIXED: Arthur's "FATAL ERROR: 17" on the MEGA65 was a missing window property.

get_wind_prop's property 13 is the font size: height in the high byte of the
word, width in the low one. window_font_size was declared in screen-z6.asm and
never written, so it read back as 0. txd shows what Arthur does with it:

    11168:  GET_WIND_PROP   #00,#0d -> -(SP)      ; window 0, font size
    1116e:  LOG_SHIFT       (SP)+,#fff8 -> -(SP)  ; >> 8, the height
    11175:  AND             (SP)+,#ff -> G87
    11179:  GET_WIND_PROP   #00,#0d -> -(SP)
    1117f:  AND             (SP)+,#ff -> G18      ; the width

and then, at $9d54, "MOD L00,G87" - a modulo by zero.

The fix: get_wind_prop answers 1,1 for property 13, because the header tells the
game a character is one unit each way, and window_font is initialised to 1, the
normal font. Property 13 is the only window property that is a real word, so it
cannot live in the byte-per-window arrays with the others.

This was never a MEGA65 bug. The C64 executed the same modulo by zero and did
not notice, because make.rb compiles CHECK_ERRORS into MEGA65 builds only
(`if $target == "mega65"`). Both targets were also computing Arthur's whole
layout from a zero font width; with the fix, the status line and the body text
land where they should, on both.

How it was found: DEBUG + TRACE make fatalerror print the last ten opcodes with
their z_pc, which named the instruction; ztools' txd then named the property.
Both are worth reaching for early - see CLAUDE.md.

Two dead ends worth not repeating, both disproved along the way:
- It is not a large memory problem. A generated v6 story of 276 KB (1700 filler
  routines, `inform -v6 -B`) calls a routine, passes arguments to it, prints a
  string and reads globals all from above $40000, and the MEGA65 gets every
  answer right. Z-machine byte addresses are 16 bit, so loadb/loadw cannot reach
  above 64 KB anyway; only code and strings live up there, and those work.
- It is not the timed-input interrupt, which had never been tested for z6 on any
  target. A v6 test doing `@read_char 1 10 Ticker` and `@aread buf par 10 Ticker`
  gives "read_char -> 0 ticks 3" and "aread -> 0 ticks 3" on the C64 and the
  MEGA65 alike, which is correct.
- 2OP:23 is div and 2OP:24 is mod, and z_divide serves both. Tracing z_ins_div,
  finding no hits, and concluding the MEGA65's PC had diverged cost an
  afternoon. It had not: z_ins_mod fires on the C64 at the same z_pc, $009d57.

Note in passing: fatalerror's non-DEBUG path does `stx SCREEN_ADDRESS + 79`, a
cell offset used as a byte offset. Under -fcm that writes the high byte of cell
39 instead of the character of cell 79. Harmless - it is the error code, on a
screen that is about to reset - but it is the same class of bug as the three the
FCM work turned up.

Latent, and deliberately NOT fixed: two more places that can drive the print
buffer past its end, exactly as set_cursor's unclamped column did (the Shogun
40-column bug fixed in July 2026 - see CLAUDE.md). Both are one-line
speculative clamps, and neither is triggered by any of the four games today, so
they stay written down rather than written: fix them only if a real game is
actually seen to hit one. Guessing at clamps in the screen layer has its own
cost - the margins and edges feed wrapping, erasing and scrolling, and a clamp
in the wrong place would quietly change a layout no test covers.
- set_margins reads both margins with `lda z_operand_value_low_arr` (+1), the
  low byte only, so a negative margin would arrive as ~250 the way column -6
  arrived as 250. It then computes .sm_left = window_x + window_left_margin and
  can park window_x_cursor there, which start_buffering turns straight into
  buffer_index. Shogun passes 2,2 and Zork Zero small positive values, so
  nothing reaches it. If a game ever does, read the margins as signed words.
- window_size stores its width with no clamp (window_x_size = the operand's low
  byte), and s_window_right_edge trusts it: window_x + window_x_size -
  window_right_margin, with no ceiling at s_screen_width. A game that sets a
  window wider than the screen - a plausible thing for a v6 game laid out for 80
  columns to do on a 40-column screen - would let buffer_index run past
  print_buffer's SCREEN_WIDTH + 1 bytes at $100 and into the 6502 stack. Every
  window the four games set is <= the screen width (checked in play on the
  40-column MEGA65: Shogun's are 40, 40, 22), which is why this has never
  fired. The fix, if it ever does, is to clamp the edge in s_window_right_edge,
  since that is the single place the buffer's right-hand limit comes from.

Z6 on other targets
-------------------
The window model now works on every target Ozmoo supports: the C64 first, then
the Plus/4, the MEGA65, the X16, and finally the C128's 80 column (VDC) screen.
- ECM (-ecm) is C64 only, and make.rb rejects it elsewhere. The MEGA65 and X16
  don't need it: their video chips give every character its own background
  colour, so those targets should set the window's background directly rather
  than borrowing the ECM approach.

DONE: the z6 window model on the C128's 80 column screen. This was the last
target still scrolling the whole screen, and the fix is the same shape as the
X16's: .s_scroll_vdc now goes through the shared .calc_window_rect /
.sw_up_one / .sw_blank_row helpers, and only the row copy (.vdc_copy_row) is
VDC-specific. s_scroll_window's "80 columns are not handled" early return is
gone, so the scroll_window opcode works there too.
- The VDC's screen is not in the CPU's address space, but the chip has a
  blitter: with the copy bit of the vertical scroll register (24) set, writing
  a byte count to VDC_COUNT (30) copies that many bytes from the copy source
  address (32/33) to the current address (18/19). So a window row is one
  register write instead of 80 read/write round trips through the data port.
  Characters live at $0000 and their attributes at $0800, so a row is copied
  twice, once per region (the attributes only under COLOURFUL_LOWER_WIN, which
  z6 always sets, since Z6 implies Z5PLUS).
- A count of 0 means 256 bytes, not none, so .vdc_copy_row returns early for a
  window with no columns rather than blitting a quarter of the screen.
- .sw_blank_row needed nothing: it blanks through s_delete_cursor, which
  already dispatches to VDCPrintChar in 80 column mode. Note that it does so
  before loading y from zp_screencolumn, so y must hold the column on entry -
  which every caller already arranges.
- The old .s_scroll_vdc also refused to scroll until the cursor had passed the
  bottom of the *screen* (its "cmp s_screen_height / bpl" guard), which is the
  same bug the X16's had: a window that did not reach the bottom never
  scrolled at all. The caller has already checked the window's own edge.
Verified under VICE (x128) by dumping VDC RAM through the monitor - the screen
is not in the CPU's address space, so the dump needs "bank vdc; m 0000 07cf" as
one command, and note that VICE's -80col does not reach the kernal's 40/80 flag
under -default, so the test pokes $d7 = $80 at program_start instead (a
tracepoint on program_start with "> d7 80"). testz6scroll then renders on the
VDC exactly as it does on the C64: the window scrolls to "line 6".."line 10"
and the screenful of '#' around it survives intact on all four sides. testz6
lays out both windows at 80x25 and its two scroll_window calls both run. The
C128's 40 column mode is unchanged (it takes the same CPU path as the C64, and
its dump is identical).

DONE: the z6 window model on the X16 (text only, VERA's 80x60 screen). The X16

DONE: pictures on the X16 (-pics without -fcm; make z6-pics-x16 /
arthur-pics-x16, and the other three games have targets too). The design is
the MEGA65 FCM engine ported to VERA (asm/pictures-x16.asm; the shared
opcode plumbing in screen-z6.asm now splits per target around the engine):
- The screen is two layers: text stays on layer 1, and the pictures live
  behind it on layer 0, a 64x32 map of 16x8-pixel 4bpp tiles. VSCALE is
  halved and VSTOP crops to 640x200 effective - the MEGA65 80-column
  geometry, so `dfrotz -h 25 -w 80` and the MEGA65 build stay the
  references. SCREEN_HEIGHT is 25 under Z6_PICTURES (constants-x16.asm)
  and the build reports interpreter 6 (IBM), like the MEGA65 pics builds.
- One tile is one logical art cell (8x8 art pixels doubled horizontally at
  bake time). The store is all of VRAM bank 0 - 1024 tiles, tile 0 reserved
  as the transparent tile - and the map, the relocated charset and the text
  screen share bank 1. A map entry carries the tile index and a palette
  offset nybble, which is how each picture keeps its own 16-colour bank
  (banks 1..14 above the text colours): the bank rides in the map cells,
  not the pixels, so nothing is rebaked when a bank is reassigned.
- No preload: a picture is LOADed from SD on demand, uncompressed, into a
  4-bank staging area just above the story (PIC_STAGING_BANK from make.rb),
  and the staged picture is cached so redrawing the frame or the status
  icons never touches the card. No picture disks, no swap prompts - Zork
  Zero's 396 files just sit in the game directory. picture_data answers
  from assembled-in pic_width/pic_height tables (the picture asked about
  is usually not the one staged), which pics2asm's --x16 mode emits.
- The allocator, the GC (compact instead of wrap) and per-pixel
  compositing are the MEGA65's, reworked for VERA's data ports: the GC
  walks the layer 0 map instead of screen RAM, and a composite cell has
  ONE palette bank, so pixels kept from the underlying picture are
  translated into the overlay's bank (exact colour match, else nearest by
  RGB distance over CPU-side palette copies).
- The text layer cannot bury a picture the way a one-plane screen does, so
  drawing a picture blanks the text cells it covers (space, background
  nybble 0 = transparent) - the MEGA65's replace-the-text semantics -
  and erase_picture / erase_window restore opaque background and clear the
  layer 0 cells. The undo buffer moved from VRAM (which the tile store now
  owns) to banked RAM above the staging area; quit restores the composer
  and switches layer 0 off so BASIC comes back readable.

Picture store: multi-disk (done) and the 255-picture cap (open)
--------------------------------------------------------------
DONE: pictures no longer share the boot disk. pics2asm.py packs the numbered
picture files across as many mega65_<game>_pics_N.d81 disks as they need (one
d81 each, filled in turn; picdisks.txt records the assignment and pic_disk is
the assembled-in table), make.rb's build_picture_disks builds them, and
pic_load_all sweeps the disks at boot. For each disk it tries the second drive
(boot_device + 1) then the boot drive, reading the drive error channel to tell
a present file from a missing one (a missing file OPENs "successfully" and
hands back a stale buffer page, so the status byte lies), and only asks for a
swap if neither drive holds it. make.rb auto-mounts -9 with the first picture
disk when it launches xemu, so a one-disk set (Arthur, 137 pictures, ~1950
blocks) loads with no prompt. Verified headless: Arthur reaches its restore
prompt from -8 boot / -9 pics with no swap. Picture numbers now run to 999
(pic_number_lo/hi, rect_number_lo/hi, three-digit P### names).

DONE: the per-build picture count is now 16-bit, so a build can hold up to 999
pictures (pics2asm.py's cap). .pic_index is a word, the parallel pic_* tables
(pic_number_lo/hi, pic_disk, pic_page_lo/hi, pic_adaptive) are indexed through
.pic_addr - which forms base + word index in .pi_ptr (z_temp + 10) and reads
(.pi_ptr),y - instead of the old ,y that capped at 256, and pic_win_number is a
word per window so two pictures 256 apart no longer alias a window's tile run.
make zorkzero-pics-mega65 builds Zork Zero's 396 pictures (numbered to 504) over two
picture disks. Verified headless: it loads all 290 pictures of disk 1 from
drive 9 (indices past 255) and then correctly prompts for disk 2. Confirmed on
xemu: Zork Zero loads from both picture disks and starts, and drawing the
pictures works.

DONE: the disk swap itself is confirmed by hand (July 2026). Headless testing
can only reach the "insert picture disk N" prompt, since xemu cannot swap a
disk, so this was the last part of the multi-disk path that no automated run
could reach. It works: the prompt is answered by swapping the disk in the
drive, and the load continues into the second disk's pictures.

Journey is the next size up to try (more pictures still).

IDEA, future consideration: a single MEGA65 D65 disk instead of picture-disk
swapping. The MEGA65's HD-floppy image format (.d65) holds roughly double a
d81 - about 1.6 MB for a standard HD floppy (the F011 controller and the
image format can express larger, variable geometries, ~2.7 MB and up in the
64-sectors x 85-tracks "superfloppy" layout, but the numbers are not cleanly
pinned down publicly and the format has moved over time). One d65 would fit
Zork Zero's two picture disks (and probably Journey's), removing the swap
prompt AND the need for a second drive: on real hardware the swap exists only
because most machines have just the internal drive (device 8), and our "two
drives then swap" logic (pic_load_all) is the fallback for that.

Why this is promising: on the MEGA65 the KERNAL/HYPPO and CBDOS already read
d65 through the standard file OPEN/LOAD path (the hypervisor and freezer gained
.d65 support years ago), so Ozmoo's disk.asm would likely need little more than
dropping the per-disk grouping and the swap prompt - the reads themselves go
through the same DOS. The directory would need to hold all ~396 files on one
disk; the d81's ~296-file limit was the second reason for two disks (separate
from the 800 KB capacity), so confirm the d65 directory chain actually scales
before assuming one disk is enough.

Two hard blockers for OUR workflow, which is why this is future-only:
  1. xemu does NOT mount d65 (it is a TODO in xemu, not implemented - lgblgblgb
     /xemu#140). Our entire MEGA65 test path is headless xemu, so we could not
     test a d65 build at all, headless or windowed, without real hardware.
  2. VICE's c1541 cannot CREATE d65 (it knows d64/d71/d81/d80/d82/d90 only).
     make.rb's whole disk-building pipeline is c1541, so we would have to write
     a d65 authoring tool - a d65 variant of pics2asm/build_picture_disks that
     lays out the MEGA65 BAM and directory itself, or drive mega65_ftp / the
     MEGA65 tools. The format is only semi-documented (c65gs blog, mega65-core),
     which makes a from-scratch writer real work.

Estimate: feasible on real hardware and genuinely nicer there (one disk, one
drive, no swap), but currently impractical to build or test with our tooling
until both xemu-mount and a Linux d65 writer exist. Worth revisiting when xemu
adds d65, or if a maintained d65 creation tool appears. A closer-in alternative
that needs no new format is to mirror the X16: load MEGA65 pictures straight
from the SD card on demand (as pictures-x16.asm does from SD), bypassing d81
containers entirely - that reuses the on-demand-load design we already have and
sidesteps both blockers, at the cost of MEGA65 SD/HYPPO access code.


The plan for z6 on the MEGA65
-----------------------------
The C64 and the Plus/4 will never draw pictures, and keep the "pic:N" notes
whatever happens below.

Screen size, and why 320x200
  Arthur was an Amiga game at 320x200, and z6games/arthur-graphics is scaled to
  that: all 137 pictures fit, the largest being 292x196. So the MEGA65 z6 screen
  is 320x200 in FCM with 16 bit character codes: 8x8 cells, 40x25 of them.

  That is not only the natural fit for the art, it is the only size that fits in
  memory. An FCM cell needs 64 bytes of character data, so a worst case full
  screen picture is 1000 x 64 = 62.5 KB of tiles. At 640x400 it would be 80x50 =
  4000 cells = 250 KB, and there is nowhere to put that. Screen RAM (2000 bytes)
  and colour RAM (2000 bytes) at 40x25 with two bytes per cell are exactly the
  sizes the current 80x25 8 bit mode already uses, so neither grows.

  Fast RAM is 384 KB, and the techreport's map spends most of it: $00000-$0ffff
  interpreter, $20000-$3ffff ROM, $40000-$4ffff sound effect, $50000-$5ffff undo.
  That leaves bank 1, $10000-$1ffff, 64 KB, unclaimed. 62.5 KB of tiles fit there
  with 1.5 KB to spare, so sound and undo both survive and nothing has to be
  sacrificed. It is knife-edge, and it assumes two things that step 2 has to
  confirm: that C64 mode really leaves bank 1 alone, and that the text charset
  can live outside those 64 KB, as ordinary 8 byte glyphs for chars 0-255 with
  full colour only for chars 256 and up (what the VIC-IV's FCLRLO/FCLRHI split is
  for). There is no room for double buffering. If it does not fit, free
  $40000-$4ffff by dropping sound before giving up any of the above: z6 games do
  not use extended sound.

  8 bits per pixel, not the 4 of NCM, even though no picture uses more than 14
  colours and NCM would halve every figure here. An NCM cell is 16 pixels wide
  and a pixel is a nybble, so a picture at an odd x needs a nybble shift, which
  the DMA engine cannot do and which lands us back in CPU side bitmap shifting.
  At 8bpp a pixel is a byte, any x offset is a byte offset, and m65_run_dma blits
  it directly. Revisit only if memory forces it, or if step 2 shows Arthur's
  draw_picture coordinates are always cell aligned.

  Dropping to 40 columns is right for v6 and wrong for everything else, so this
  is a Z6-conditional fork of the MEGA65 constants, not the new MEGA65 default.
  constants.asm sets SCREEN_WIDTH = 80 for the target unconditionally today.

1. DONE for the MEGA65, against the C64. The earlier headless run stopped at
   the first MORE prompt; driving the prompts from xemu's uartmon (the recipe
   is in CLAUDE.md) gets testz6 all the way to the read prompt. Running the
   same story on both targets and dumping screen and colour RAM:
   - Every line matches, character for character, once each window is scaled to
     its screen width. window_size, move_window, set_margins and the wrapping
     all agree; so do print_form, picture_data, and the pic:N notes, which land
     on their window's top left cell (col 12 on the C64, col 25 on the MEGA65,
     each being the window's x).
   - The MORE prompt appears at the current window's bottom right cell on both.
   - Colour RAM is a clean 8 x 13 rectangle of colour 3 on the C64 and 8 x 26
     on the MEGA65, matching @set_colour 8 7 1 and nothing smeared. That
     exercises the colour2k/colour1k banking in s_scroll_window.
   - testz6 scrolls -1 then +1, which a scroll_window that did nothing would
     also pass. Rebuilt with a single +1 scroll, both targets shift the window
     up one row and both then let erase_picture blank the first five characters
     of "pics 0 rel 0", which the scroll moved under the note. So it really
     scrolls, identically.
   The one apparent difference is a red herring: the MEGA65 dump shows $e0
   where the C64 shows "p", at the start of the pic:12 note. $e0 is CURSORCHAR
   (ozmoo.asm), and draw_picture is supposed to leave the cursor where it found
   it, which is exactly there. The C64 dump was simply taken before the cursor
   was drawn.

   DONE for the Plus/4 too, the same way, under xplus4 (screen $0c00, colour
   $0800). Both builds are character for character identical to the C64, in the
   double scroll and the single scroll variants alike. Its colour RAM holds $63
   inside window 1, which is TED colour 3 at luminance 6 - the right mapping of
   the C64's cyan through plus4_vic_colours, not a low nybble that happens to
   read 3.

   So the three targets that share .s_scroll agree. Nothing here needs fixing
   before the FCM work starts.

2. DONE. tools/png2fcm.py and tools/fcm-prototype.asm; the prototype draws
   Arthur's title screen, and then a smaller picture with a line of text under
   it, on a 320x200 FCM screen with 16 bit character codes. What it settled:

   - Bank 1 is free and the VIC-IV can fetch from it. Tiles DMA'd from the
     program's own RAM to $10000 render.
     Confirmed inside Ozmoo since: stamping 64 signatures across $10000-$1ffff
     at testz6's read prompt and then letting the game finish the read, print,
     scroll its window and quit leaves every one of them intact. Statically,
     every far write in the MEGA65 build goes somewhere else - dynmem and the
     story to attic (dynmem_pointer + 3 = $08, ozmoo.asm), the current sound
     effect to bank 4 (sound.asm), undo to bank 5 (disk.asm, lda #$05),
     scrollback to attic and colour RAM. Nothing addresses bank 1. Not
     exercised at runtime: save, restore, undo, sound, scrollback.
   - The register setup that works, all with hot registers off ($d05d bit 7):
     $d031 = H640 off, V400 off, and ATTR (bit 5) OFF, which is what gives
     8 bit colour - the opposite of what some of the documentation says.
     $d054 = CHR16 (bit 0) on, FCLRHI (bit 2) on, FCLRLO (bit 1) OFF.
     $d05e = 40 chars per row, $d058/9 = 80 bytes per row (two per cell),
     $d060-3 = screen, $d064/5 = colour RAM offset, $d068-a = charset.
   - In FCM the 16 bit screen code is not a character number: it is the pixel
     data address divided by 64. Tiles at $10000 are screen code $0400.
   - FCLRLO off does what we hoped: codes < 256 are ordinary 8 byte glyphs
     from CHARPTR, codes >= 256 are 64 byte full colour tiles. Text and
     picture coexist on one screen. So the text charset costs 2 KB and lives
     outside the tile store, as the budget in step 3 assumes.
   - The palette registers want the nybbles swapped. This is easy to get wrong
     and hard to see: every colour in 1.png is of the form $NN, for which
     swapping is a no-op. Checked against 40.png, whose palette has values like
     $F0; unswapped, its (0,0,240) blue renders as (0,0,8). Swapped, the whole
     picture is exact.
   - Colour RAM is two bytes per cell. Byte 0 is flags (zero), byte 1 is the
     colour for pixel value 255, which no picture pixel is. A single DMA fill
     of zeroes over both is enough.
   - Pixel 0 is transparent and shows the background, so padding a picture out
     to a cell boundary costs nothing visually.
   - Deduplicating cells is worth having and nearly free. Across the 137
     pictures it saves 13% (1155 KB -> 1002 KB). The worst single picture,
     84.png, is 925 cells: 57.8 KB raw, 46.9 KB deduped. Either fits bank 1's
     64 KB, so the step 3 budget holds with room to spare. png2fcm.py always
     dedupes and emits a cell map, which is what screen RAM wants anyway.
   - Not tested: whether DMA can do the scrolling. Nothing suggests it cannot -
     scrolling is a linear copy within screen and colour RAM, and DMA already
     writes colour RAM here - but it has not been run.

   One trap for anyone reading the prototype: it fills screen RAM for all 25
   rows from the cell map, so a picture shorter than the screen ran off the end
   of the map until a row check was added. Arthur's title screen is exactly 25
   cells tall and hid the bug.

3. Rewrite the MEGA65 z6 screen mode to use FCM (full colour mode, VIC-IV,
   with 16 bit character codes) at 320x200, 40x25 cells, as argued above. It
   is needed either way: it gives every character its own background colour,
   which retires the ECM approach on this target, and 16 bit character codes
   are the only sane way to get enough unique tiles for pictures.

   The size of the change is now known. screenkernal-z6.asm has 66 uses of
   zp_screenline / zp_colourline, and nearly all of them are "y holds the
   column, sta (zp_screenline),y writes the cell". Under CHR16 a cell is two
   bytes, so every one of those is affected. Two seams make it tractable:
   - update_screenpos already computes the row address on the MEGA65 with the
     hardware multiplier from s_screen_width, so it only needs to multiply by
     80 instead of 40.
   - if zp_screencolumn holds the byte offset (column * 2) rather than the
     column, the store sites stop caring. What then has to change is the
     comparisons against the screen width, the increments (+2, not +1), and
     the few places that convert to and from a real column: s_plot,
     cursor_column, s_window_left_edge / s_window_right_edge.
   Do it behind a build flag so the existing MEGA65 build keeps working while
   this lands, and keep it in screenkernal-z6.asm unless the !ifdefs get out of
   hand; on this evidence a whole forked file would be mostly duplication.

   3a. DONE: text at 40x25. -fcm, mirroring -ecm, sets Z6_FCM_MODE. It is
   rejected on any target but the MEGA65, on any version but 6, and alongside
   -ecm. testz6 under -fcm is now character for character identical to the C64
   at 40 columns, and the colour rectangle matches too. The C64, C64 -ecm,
   Plus/4 and plain 80 column MEGA65 builds are unchanged.

   What the design turned out to be:
   - zp_screencolumn stays a column. Only the sites that index the screen
     double it. That leaves the window edges, the margins and every comparison
     alone, and it never escapes screenkernal-z6.asm.
   - zp_colourline is biased by one, so the same doubled index writes the
     character (the even byte of a screen cell) and the colour (the odd byte of
     a colour cell). A row starts at a multiple of 80, so the bias never
     carries.
   - The other two bytes of every cell, the screen's high byte and the colour's
     flags, must be zero and stay zero. init_mega65 clears both once.
   - Reverse video still works: the C64 charset's codes 128-255 are the
     reversed glyphs, so ora #$80 does the right thing when CHARPTR points at
     it. No need for the ECM compromise.
   - CHARPTR points at $2d000, the C64 font in the MEGA65's ROM. Bank 1 is
     therefore entirely free for tiles after all, and the 2 KB reservation the
     plan above assumed is not needed. Revisit for CUSTOM_FONT.

   Three traps, all of which produced a screen that looked nearly right:
   - Most text does not go through s_printchar. It goes through
     print_line_from_buffer in screen-z6.asm, which writes the screen directly.
     Miss that and the text lands one byte per cell.
   - The MORE prompt's cell address is computed from zp_screencolumn as a byte
     offset (.set_more_prompt_pos, and the SCREEN_WIDTH*SCREEN_HEIGHT-1 in the
     .more_access defaults).
   - .s_scroll advances a row with "adc s_screen_width", which is the row's
     byte count on every other target but half of it here.

   Still to do for the screen layer: erase_window and scroll_window were only
   exercised through testz6; the cursor, delete and s_erase_line_from_cursor
   paths are converted but barely tested. Nothing sets a per window background
   colour yet, which is the whole point of FCM for text, and is what retires
   ECM on this target.

   The charset goes at $10000, the bottom 2 KB of bank 1, with the tile store
   from $10800 up. FCLRLO is off, so codes below 256 fetch 8 byte glyphs from
   CHARPTR, and CHARPTR has to point at RAM the VIC-IV can read. Bank 1 is that
   RAM, we own it, and 2 KB out of 64 leaves 62 KB, which still holds the worst
   deduped picture (46.9 KB) with room. The prototype copies the charset out of
   the C64 character ROM, which appears at $d000 while CHAREN (bit 2 of $01) is
   clear; the real build should do the same, or honour CUSTOM_FONT.

4. Graphics. The drawing is not the hard part.

   4a. DONE: Ozmoo draws real pictures on the MEGA65, out of attic RAM.
   `ruby make.rb -t:mega65 -fcm -pics tools/testpics testz6.z6`. The pictures in
   tools/testpics are ours, generated by tools/gen_testpics.py; testz6 draws
   them. Without -pics the build still writes the "pic:N" notes.

   The shape of it, which is the same shape Arthur will need:
   - tools/pics2asm.py writes one p<nnn>.bin per picture and a small index that
     Ozmoo assembles in. make.rb puts the files on the d81 next to zcode, and
     pic_load_all preloads them into attic RAM at $08300000 at boot, using
     m65_load_file_to_reu, exactly as sound.asm preloads the WAVs. Nothing but
     the index and the picture numbers is embedded in the interpreter.
   - A picture file is: cells wide, cells high, tile count, a 48 byte palette,
     a cell map of two bytes a cell, then the tiles at 64 bytes each.
   - Drawing reads the header and palette straight from attic, allocates the
     window a run of the tile store, copies the tiles down into bank 1, and
     fills the cells. A cell's screen code is its tile's address / 64, so it is
     $0400 + slot + index.
   - The palette bank is the window's, not the picture's: a window holds at most
     one picture, so eight banks of 16 above the 16 text colours are enough, and
     the bank is 16 + 16 * window. There is therefore no limit on how many
     pictures a game may have.
   - Pixel indices are stored relative to entry 16, so the tile copy adds
     16 * window as it goes. The DMA engine cannot add, so that one copy is done
     by the CPU. A pixel of 0 is transparent in every bank and is left alone.
   - Each window keeps the run of the tile store it was given, and reuses it
     when the next picture fits. When the store runs out the allocator starts
     again at the bottom, which can only spoil a picture in another window.
   - Every place Ozmoo writes a character also zeroes the cell's high byte (the
     clear_cell_high_byte macro). Without it, text printed over a picture leaves
     the cell pointing at a tile, and erase_picture's spaces do nothing. That is
     the fourth bug of exactly that shape the two-byte cell has caused.

   Two traps worth remembering:
   - make.rb upper-cases the names it puts in the disk directory, so the
     interpreter must ask for "P004", not "p004". A wrong name does not fail
     loudly: kernal OPEN reports no error, the read returns nothing, and one
     page of whatever was in the copy buffer lands in attic RAM.
   - testz6 originally drew all three pictures into window 1, which breaks the
     one-picture-per-window rule and left only the last picture's palette in the
     bank. It now draws picture 4 in window 0.

   4c. DONE: Arthur's pictures fit on a d81, and Arthur draws them.
   `make arthur-pics-mega65` leaves 28 blocks free, and the churchyard picture appears
   above the text. `make z6-pics` does the same for testz6 and the pictures in
   tools/testpics, which are ours.

   Two things were needed, and RLE alone was not enough:
   - Four bits a pixel. A picture has at most 15 colours (index 0 is
     transparent), so attic and the disk hold two pixels a byte and the tile
     copy expands them, which it can do for nothing because it already walks
     every byte to add the window's palette offset. This halves the set before
     it is compressed: 1046 KB of tiles becomes 545 KB.
   - PackBits RLE, not png2fci's scheme. A token of 0..127 means that many plus
     one literal bytes follow; 129..255 means the next byte repeats 257-token
     times. It needs no lookahead, which keeps the 6502 decoder to about thirty
     lines, and it is decompressed straight into attic as the file is read.
   Together: 545 KB -> 484 KB, and 484 + 263 KB of story = 747 KB against the
   d81's 802 KB. RLE alone on 8 bit pixels gives 746 KB of pictures, which does
   not fit; four bit pixels alone give 544 KB, which also does not fit.

   One trap: .pic_find counted its table down with `ldy #picture_count - 1` and
   `bpl`. With 137 pictures that starts at $88, which is already negative, so
   the loop compared one entry and gave up. It worked perfectly for the three
   test pictures. Count up.
   - The palette is per picture, not per set, and each picture carries its own
     16 colours. The measurements that settled that are in the git history: the
     137 PNGs hold 110 distinct palettes of at most 14 colours, and forcing them
     onto one palette is measurably lossy.
   - picture_data must start reporting real sizes and branching true, and
     z_init must stop clearing the "pictures available" bit in header_flags_2
     (see "and #(255 - 8 - 32) ; pictures and mouse never available"). Both have
     to change together, and that is what flips Arthur onto code paths no
     interpreter of ours has ever run. Expect a second round of the sort of bug
     the Z7PLUS/Z6PLUS mix-up caused: the C64 and the MEGA65 will no longer be
     playing the same game.
   - erase_picture blanks the picture's rectangle with spaces. It should
     arguably restore the window's background instead, once windows have one.
   - Nothing sets a per window background colour yet, which is the remaining
     half of step 3 and the reason FCM beats ECM for text.

When the MEGA65 work does start, this is the VIC-IV setup from the old
screenmodel-z6.asm skeleton (deleted; see git history, a7e3b56). It was never
called - the "jmp -" at the end shows how far it got - but the register names
and the full colour / 16 bit character mode setup are the starting point for
giving each window its own background colour.

    ; MEGA65 registers
    VIC2CTRL    = $d016
    VIC3CTRL    = $d031
    VIC4CTRL    = $d054
    LINESTEP_LO = $d058
    LINESTEP_HI = $d059
    COLPTR_LO   = $d064
    COLPTR_HI   = $d065
    HOTREG      = $d05d
    CHRCOUNT    = $d05e
    SCNPTR_0    = $d060
    SCNPTR_1    = $d061
    SCNPTR_2    = $d062
    SCNPTR_3    = $d063

    init_mega65
        ; set 40MHz CPU
        lda #65
        sta 0
        ;  set default colors
        lda #$00
        sta $d020
        sta $d021
        ; enable VIC-II/VIC-III hot registers
        jsr mega65io
        ; enable full color and 16 character mode
        lda VIC4CTRL
        ora #$04 ; full color mode
        ora #$01 ; 16 bit character mode
        sta VIC4CTRL
        ; enable H640, V400
        lda VIC3CTRL
        ora #$80 ; 640 pixel width
        ora #$08 ; 400 pixel height
        sta VIC3CTRL
        ; shift one pixel right (VIC-III bug)
        lda  VIC2CTRL
        ora #$01
        sta VIC2CTRL
        ; Set colour RAM offset to 0
        lda #$00
        sta COLPTR_LO
        lda #$00
        ;lda #$10 ; move colour RAM because of stupid CBDOS himem usage
        sta COLPTR_HI
        ; set characters/line
        lda #$80
        sta CHRCOUNT
        ; set linestep (2 screen bytes = 1 character, so 2*CHRCOUNT)
        lda #$a0
        sta LINESTEP_LO
        lda #$00
        sta LINESTEP_HI
        ; Set screen at $12000
        lda #$00
        sta SCNPTR_0
        lda #$20
        sta SCNPTR_1
        lda #$01
        sta SCNPTR_2
        lda #$00
        sta SCNPTR_3

        ; init screen memory
        +dma_fill $12000, 32, 4000, 2
        ; init color memory
        +dma_fill $ff80000, 0, 8000, 1

        ; Put red C in top corner
        +dma_fill $12000, $43, 1, 1
        +dma_fill $ff80000, 2, 2, 1

        ; disable VIC-II/VIC-III hot registers
        lda HOTREG
        and #$7f
        sta HOTREG

    -   jmp -
        rts

because starting a game on the 80 column screen is currently a nuisance. VICE

quick patch.

X16 pics: text drawn in colour 0 is TRANSPARENT, so it cannot cover a
picture. VERA renders palette index 0 as transparent on a layer, and
zcolours maps z-colour 2 (black) to VERA colour 0 - the commonest text
colour there is. Every cell Ozmoo prints with black as its foreground
therefore has transparent ink, and a reverse-video field (drawn entirely
in the foreground colour) is transparent edge to edge. Nobody notices
while layer 0 is blank behind the text: the backdrop is palette 0, also
black, so it looks exactly like opaque black ink. Over a picture it is
wrong, and the MEGA65 - one layer, text replaces tiles - does not have
the problem.
  Found July 2026 via a PunyInform status line: a reverse-video status bar
  printed over a picture that legitimately sat on layer 0 row 0, and the
  picture showed straight through it. Worked around at the source (see
  split_window's pic_clear_map_rows, which stops layer 0 keeping content
  under a window 1 that has just grown), which is correct in its own
  right, but does not fix the general case: any game printing text over a
  picture on the X16 will see the picture through the glyphs.
  The real fix is to stop text using palette index 0: pick a spare index
  (zcolours only reaches 0-15, and colours 16-23 - the Frotz extension -
  are what make 10-15 reachable at all), set its VERA palette entry to
  black on pics builds, and map z-colour 2 to it. Then every printed cell
  is opaque and text covers layer 0 the way it covers tiles on the
  MEGA65. Do it behind Z6_PICTURES so the text-only X16 build, which is
  verified and has no layer 0, is untouched.
